# RUNSHOES — 신발 데이터 확장: 카탈로그 파이프라인 설계

상태: **설계 확정(2026-10-21, 세대 포함으로 개정).** 스키마는 `V4__shoe_generations.sql`(작성 · 로컬 검증, 운영 미적용).

목표는 라인 약 240개를 **현행 + 직전 1세대**로 넣는 것이다. 합치면 약 450켤레다(4장). 리뷰 2,500~3,000건은 신발을 적재한 다음 단계에서 생성한다(8장).

이 문서를 쓰는 동안 한 일은 읽기뿐이다. 운영 `GET /api/shoes`, 후보 사이트의 robots.txt · 약관 · API 문서를 읽었고, KicksDB는 20켤레까지만 시험 조회했다. 수집 · DB 변경 · 리뷰 생성은 하지 않았다.

## 1. 지금 20켤레

- **출처:** 크롤러로 모은 데이터가 아니다. 모델명으로 웹 검색해 다나와 상세 페이지를 찾아 보면서 **손으로 채웠다**(사용자 확인). 커밋 이력에서도 사람이 여러 번 고친 흔적이 보인다.
  - `a121188` → `e2bfdc4` → `84caa9d`(2026-07-21)
  - 바뀐 것: 페가수스 41 → 42, 정가 159,000 → 169,000, 스택 0 → 37 → 36, 미드솔 필드 추가
- **편집 값:** purpose · stability · width · summary · description은 사이트가 직접 판단하고 쓴 값이다. 수집 대상이 아니다.
- **이미지:** 상품 사진을 받아 배경을 지운 것이다. 1120×1120, 102장, 13MB이고, 대부분 확장자만 `.png`인 WebP다. 앱 컨테이너 이미지 안에 들어 있다(`Dockerfile`의 `COPY public`).
- **운영 DB:** 저장 필드 17개가 시드(`db.json` = V2)와 같다.
- **분포:** 용도는 조깅·회복주 6 · LSD·장거리 4 · 템포·인터벌 4 · 레이스 3 · 트레일 3이다. 안정화는 1/20(젤 카야노 32)이다.
- **세대:** 12켤레가 지난 세대다(부록 A).
  - 이 12켤레는 **그대로 두고 직전 세대로 쓴다.** 현행 세대를 새 행으로 더한다(3.2).
  - 리뷰 104건은 옛 행에 그대로 남는다.

## 2. 수집처

### 2.1 필드별 출처

| 필드 | 출처 | 방식 |
|---|---|---|
| **모델 목록**(라인 + 현행 세대) | 브랜드 공식몰의 러닝 라인업 | 사람이 라인업 페이지를 보고 후보 목록(`candidates.csv`)을 만든다(4장) |
| **사실 스펙**(weight · drop · stackHeight · midsole · carbon · wideAvailable · price) | 공식몰 상품 페이지 + 모델별 웹 검색(리뷰 매체 · 브랜드 보도자료) | **필드마다 출처 URL을 남긴다**(`sources`, 6장). 가격은 **정가만**(국내 공식몰 → ABC마트, 2.2.2) |
| **이미지** | KicksDB → StockX 이미지 URL | **핫링크. 저장하지 않는다**(5장) |
| **편집 값**(purpose · stability · width) | 사람 | 후보 목록 단계에서 붙인다 |
| **글**(summary · description) | 생성 | 8장 |
| **리뷰** | 생성 | 8장 |

**스펙 대조 규칙:**
- 공식몰 값이 있으면 그것이 기준이다.
- 웹 검색 값과 무게 10g 이상, 스택 2mm 이상 차이 나면 `review`로 둔다.
- 공식몰이 공표하지 않은 값(호카의 미드솔 등)은 출처가 있는 값만 넣고, 없으면 `null`이다.

**요청 예절(공식몰 · 웹 검색 페이지):**
- 도메인당 5초에 1회 이하, 동시 요청은 1개다.
- 받은 페이지는 로컬에 캐시한다.
- User-Agent에 프로젝트 이름과 연락처를 넣는다.
- 403 · 429 · 캡차가 나오면 그 도메인은 그날 멈추고 수동으로 넘긴다. **우회하지 않는다.**
- robots.txt와 약관을 확인한 날짜를 `catalog/sources.yaml`에 적고, 적은 도메인만 자동으로 받는다.

### 2.2.1 약관 해석 기준(2026-10-24 사용자 결정)

같은 질문이 다시 나오면 이 기준으로 판정한다. 법률 자문이 아니라 이 프로젝트의 수집 기준이다.

- **일반 지재권 조항은 사실 값에 걸리지 않는다.** 한국 쇼핑몰 약관 대부분(공정위 표준약관)에 "이용자는 … 회사에 지식재산권이 귀속된 정보를 회사의 사전 승낙 없이 복제, 송신, 출판, 배포, 방송 기타 방법에 의하여 영리목적으로 이용하거나 제3자에게 이용하게 하여서는 안 된다"가 있다. 이 조항의 대상은 **지재권이 귀속된 정보**(글 · 사진 · 디자인)다. 무게 · 드롭 · 스택 · 가격 같은 **사실 값은 지재권 대상이 아니므로 해당하지 않는다.** 그래서 글 · 사진은 옮기지 않고 사실 값만 쓴다.
  - 같은 문구가 있는 곳(원문 확인): 아식스 제29조 ② · 살로몬 제24조 ② · 알트라 제20조 ③ · 뉴발란스 회원 의무 조항(“서비스에 게재된 자료를 영리 목적으로 이용하거나 제3자에게 이용하게 할 수 없”) · ABC마트 제22조 ② · 다나와 일반 약관 제24조 ②. 써코니 · 브룩스 · 머렐은 robots가 `/member/`를 막아 2026-10-24에 다시 읽지 못했다(10-21 기록상 같은 표준 조항 번호).
- **판정이 갈리는 경우 — 사실 값을 스스로 권리 대상으로 선언한 곳:** 다나와 판매점 약관 제17조 ①처럼 "가격정보" 같은 사실 값까지 회사 저작물이라고 명시하면 쓰지 않는다. 일반 조항과 다른 점이 이것이다.
- **자동 수집을 직접 금지하는 조항**(나이키 5조 "데이터 마이닝, 로봇, 스크래핑" · 알트라 글로벌 · 리닝 · 특步 · Running Warehouse)이 있거나 **robots가 필요한 경로를 막으면** 쓰지 않는다.
- **비영리 이용까지 막는 조항은 따로 본다:** 미즈노 KR 제22조 2는 지재권 정보를 "이용(영리·비영리, 변형 및 재가공 포함)하거나 제3자가 이용하게" 하는 것을 막는다. 대상은 역시 지재권 정보라 사실 값은 해당하지 않는다고 보지만, 문구가 더 엄격해 별도로 표시해 둔다. 미즈노 국내몰에 기대는 행은 18행(현행 12) — 정가 18 · 와이드 10(true 6 · false 4) · 직전 세대 존재 확인 3.
- **푸마 KR 제24조 ⑤**는 "개인적이고 비상업적인 용도" 밖의 복제를 막는다(자료 · 소프트웨어 대상). 비상업 포트폴리오의 사실 값만 쓴다.
- **검색 요약에서 읽은 값**은 페이지 수집이 아니다(Fleet Feet 약관 9조의 spider/crawl/scrape 금지와 다르다 — 사용자 2026-10-24). 다만 같은 값을 뒷받침하는 다른 출처가 있으면 그쪽을 주 출처로 둔다.

### 2.2.2 가격은 정가만(2026-10-28 사용자 결정)

- **정가만 쓴다.** 할인가 · 최저가 · 쿠폰가는 어느 소스에서든 쓰지 않는다 — 오늘 그 가게 값일 뿐 내일 바뀌고 다른 데선 또 다르다.
- 소스: ① 국내 공식몰 정가(`specs-store-price.jsonl`) ② **ABC마트 상품 페이지의 메인 표시가**(정가 — 아래 2.2.3). 같은 행에 둘 다 있으면 공식몰이 먼저다(ABC 는 빈 칸만 채운다).
- **"참고가로 통일"(다나와 · 쿠팡)은 취소했다(같은 날).** 웹 검색 100행 시험에서 다나와 공식판매처 23행(23%) · 쿠팡 0행이었고, 값이 최저가(할인가)라 기준이 맞지 않았다. 모은 값은 DB 에 넣지 않았다(스크래치패드에만). build 의 `PRICE_REF=1` 경로는 쓰지 않는다.
- 범위 1만~60만 원(하한은 2026-10-28 사용자가 5만 → 1만 — 0원 · 1원 같은 오류만 거른다).
- **가격 메타(V5):** `price_source`(`공식몰` · `ABC마트`) · `price_checked_at`(읽은 날 — 공식몰은 받은 페이지 캐시의 `fetched_at`, ABC마트는 렌더한 날) · `price_kind`(늘 `정가`). 상세 모달의 가격 옆에 작게 `ABC마트 2026/10/28 기준`. 시드 20켤레(2026-10-29 사용자): ABC마트에 있으면 그 정가로 바꾸고, ABC · 공식몰 둘 다 없으면 사용자가 다나와에서 넣은 값을 두되 `price_source` = `다나와`, `price_checked_at` = 그 값이 `db.json` 에 들어간 커밋 날짜, `price_kind` = null(정가인지 기록이 없다). 판단은 `decisions.json` rows 의 `price_krw` · `seed_only_price_meta`.

### 2.2.3 ABC마트 — Playwright 렌더링(2026-10-28 사용자 승인)

- **근거:** robots `User-agent: * / Allow: /`(2026-10-28 확인), 약관에 자동 수집 금지 조항이 없다. 제22조 ②는 일반 지재권 조항이라 사실 값(정가)에는 걸리지 않는다(2.2.1). 목록이 JS 렌더링이라 브라우저로 읽는다 — 차단을 넘는 것이 아니라 공개 페이지를 읽는 방식이다.
- **조건:** UA 는 HeadlessChrome 기본값 뒤에 우리 UA 를 붙인다(일반 브라우저로 위장하지 않는다). 차단 신호(캡차 · 403 · 429 · 챌린지)가 보이면 그 호스트는 그 실행에서 멈춘다. 요청 사이 5초, 이미지 · 글꼴 · 미디어는 받지 않는다, GPU 끔. **숫자(정가) · 스타일코드 · 상품 주소만** 저장한다 — 후기 글 · 상품 설명 · 사진은 저장하지 않는다.
- **주소 규칙(사용자 변경):** 사이트맵 색인 · 검색 결과에 더해 **그 사이트 안의 링크**를 따라가도 된다(브랜드 페이지 · 카테고리 · 러닝 전문관 → 상품 페이지). 외부로 나가는 링크는 따라가지 않는다. 사이트 검색창에 낱말을 넣어 주소를 만들지 않는다.
- **읽는 값:** 상품 페이지의 메인 표시가(정가). "최대 혜택가"(쿠폰 · 카드)는 받지 않는다. 스타일코드를 StockX sku 와 대조한다 — 같은 스타일의 상품이 있으면 그 정가, 없으면 이름이 같은 남성 · 공용 상품들의 정가가 하나로 같을 때만. 여성 상품 · 와이드(2E/4E · "와이드") 상품은 가격에 쓰지 않는다.
- **발볼(사이즈 추천 통계)은 쓰지 않는다**(사용자): 시험 11행이 전부 "보통"이었다 — 구매자가 자기 사이즈 기준으로 평가해 "적당함"이 높게 나와 변별력이 없다.

## 3. 세대 구조와 같은 신발 판정

### 3.1 세대 구조 — V4

| 컬럼 | 뜻 | 값을 만드는 곳 |
|---|---|---|
| `line_key` | 같은 라인을 묶는 키. `<brand>:<line>` 소문자 영문 슬러그(`asics:gel-kayano`, `newbalance:880`) | **후보 목록의 라인 행**에서 온다. 수집은 라인 단위로 돌고, 그 라인의 세대들이 같은 `line_key`를 받는다. **모델명을 파싱해 거꾸로 만들지 않는다** |
| `generation` | 세대 번호(`v15` → 15) | 후보 목록의 세대 칸. 번호 없이 나온 첫 모델(메가블라스트, 엘립스 등)은 1이다. 다음 세대가 "2"로 나오면 자연스럽게 이어진다 |
| `is_current` | 지금 출시돼 팔리는 가장 새 세대인가 | 후보 목록이 정한다. 새 세대를 넣는 적재기가 같은 `line_key`의 옛 행을 `FALSE`로 바꾼다(9장) |

- **키:** `UNIQUE (line_key, generation)`이다. 한 라인의 한 세대는 한 행이다.
- **세 컬럼 모두 NULL을 허용한다.**
  - 지금 앱(`Shoe` 엔티티, `POST /api/shoes`)은 이 컬럼을 모른다. NOT NULL이면 관리 화면의 신발 등록이 실패한다.
  - 엔티티와 API가 세 값을 주고받게 된 뒤(적재 단계) **V6**에서 NOT NULL로 조인다.
  - V3 머리말이 "V4"로 미뤘던 정리(`shoes.liked` · `reviews.liked` 삭제, `reviews.user_id` NOT NULL)도 V6으로 간다(V5는 정가 메타만 — 한 마이그레이션에 한 목적). V3는 이미 적용돼 주석을 고칠 수 없다.
- **기존 20켤레:** V4가 id별 고정 표로 채운다. 이 표는 사람이 정한 것이다(부록 A).
  - 가드 SELECT가 20켤레가 시드와 같은지 먼저 본다. 다르면 ERROR 1242로 멈추고 DB는 V3 그대로다.
- **로컬 검증(2026-10-21):**
  - 빈 MySQL 8.0.46에 V1~V4를 적용했다. 20켤레가 채워지고, 같은 (라인, 세대)를 다시 넣으면 ERROR 1062로 막힌다. 세 컬럼 없이 넣는 INSERT(지금 앱)도 된다. 시드가 다르면 가드가 막는다.
  - V4를 넣은 jar로 계약 `v3`를 돌렸다: **PASS 112 · FAIL 0**. 응답은 바뀌지 않았다.
  - 운영에는 적용하지 않았다. 적용은 스키마 변경 배포라 자동 Sync를 끄고 사람이 한다(런북 방식).

### 3.2 기존 20켤레와 이어 붙이기

- **방향(확인함): 맞다.**
  - 현행 세대를 **새 행**으로 넣고, 기존 행은 `is_current = FALSE`로 두어 직전 세대가 되게 한다.
  - 리뷰는 `reviews.shoe_id`로 기존 행에 붙어 있으므로 손대지 않아도 그대로 산다. 찜(`likes`)도 같다.
  - 바꾸는 것은 V4의 세 컬럼뿐이다.
- **예외 하나 — 엔돌핀 스피드 4:**
  - 현행이 6이라 4는 **두 세대 전**이다. "직전 1세대까지" 규칙으로는 들어갈 수 없는 행이다.
  - 그래도 리뷰가 붙어 있으므로 **지우지 않는다.** 6(현행)과 5(직전)를 새로 넣으면 이 라인만 세 세대가 된다.
- **스피드크로스 6:** 현행으로 둔다(`is_current = TRUE`).
  - 7은 영국 가격비교 목록 한 곳에만 보이고 살로몬 공식 자료가 없다.
  - 후보 목록을 확정할 때 공식 라인업으로 다시 본다. 7이 확인되면 7을 새 행으로 넣고 6은 직전이 된다.
- **알파플라이 3:** 4가 9-17 한정 출시, 10-29 정식 출시다. 4를 현행으로 보고 3은 직전이다.

### 3.3 같은 신발 판정

**판정 단위:** "브랜드 + 라인 + 세대"가 한 행이다.
- 하나로 합치는 것: 성별 · 폭(2E/4E) · 색상 · 품번 차이. 와이드가 있으면 `wideAvailable=true`다.
- 넣지 않는 것: GTX(방수) · 아동(GS/PS/TD) · 콜라보 · 특별판.
- 다른 라인으로 보는 것: 스펙이 다른 파생. 예: 페가수스 트레일은 페가수스와 다른 `line_key`다.
- **별칭 표 `catalog/aliases.yaml`가 라인마다 정하는 것:**
  - `line_key`
  - 한글 이름 · 세대 표기 형식 · 허용 라틴 낱말(6.1)
  - StockX 검색어(3.4)
  - 표에 없는 라인은 추측하지 않고 `review`로 둔다.
- 비슷한 이름(편집 거리 2 이하)은 "중복 의심"으로 보고만 한다. 자동으로 합치지 않는다.

### 3.4 StockX 매칭 — 세대마다

이미지를 세대마다 따로 찾는다. 시험(2026-10-21, 20켤레, 44회 호출)에서 나온 문제를 규칙으로 바꿨다.

1. **검색어는 별칭 표에서 조립한다.**
   - 라인의 StockX 검색어 틀에 세대 번호를 넣는다(예: `ASICS Gel-Kayano {n}`).
   - 한글 검색은 0/20이었다.
   - **세대마다 StockX 표기가 바뀌는 라인**은 세대별로 덮어쓴다.

     | 라인 | 세대별 StockX 표기 |
     |---|---|
     | 베이퍼플라이 | 3 → `Nike ZoomX Vaporfly Next% 3`, 4 → `Nike ZoomX Vaporfly Next% 4` |
     | 알파플라이 | `Nike Air Zoom Alphafly Next% {n}` |
     | 페가수스 | `Nike Air Zoom Pegasus {n}` |
     | 울트라부스트 | `adidas Ultra Boost {n}` |
     | 880 | `New Balance 880v{n}`("Fresh Foam" / "Fresh Foam X"가 세대마다 다르다) |
     | 호카 | `Hoka One One {line} {n}` |

2. **세대 판정 — 제목에서 세대 숫자를 낱말 하나로 읽는다.** 정규식은 `(?<![\d.])v?{n}(?![\d.%])`이다.
   - 뒤에 `%`가 붙으면 다른 신발이다. `Vaporfly 4%`는 2017~2019년의 옛 계열이라 "4"가 아니다.
   - 소수점이 붙으면 다른 신발이다(`4.5`).
   - 같은 라인의 다른 세대 숫자가 함께 있으면 `review`다(`Kayano 32 … 33` 같은 묶음 상품).
   - 검색 결과의 맨 위 대신 **판정을 통과한 것 중에서** 고른다. 시험에서 "Vaporfly 4"의 맨 위 10개가 모두 `4% Flyknit`이었다.
3. **같은 세대인지 교차 확인:** 판정을 통과한 결과들의 `sku` 앞부분(브랜드 스타일 코드, 예: 아식스 `1011C…`)이 대부분 같아야 한다. 혼자 다른 품번 계열이면 다른 세대일 수 있어 `review`다.
4. **대표 색상:** 남성용(`gender = men`)이고, 제목에 `Gore-Tex · GTX · (GS) · (PS) · (TD)` · 콜라보 · 특별판(협업 브랜드, `runDisney`, `20 Years` 같은 기념판) 표시가 없어야 한다. 그중 `rank`가 가장 작은 것을 고른다. 애매하면 `review`다.
   - **이미지 전수 대조(2026-10-24):** 적재한 224행의 이미지 제목 · 파일 이름을 모델명 · 세대와 대조했다. 같은 브랜드의 다른 모델 0, 다른 세대 0(판정 `judge`가 브랜드만이 아니라 라인 핵심 낱말 · 세대 숫자까지 본다 — 표기 차이 `infinityrn`↔`infinity run` · `1080v15` · `s/lab`은 맞는 것). 변형판 3건이 빠져나가 있었다: 방수판(클라우드서퍼 트레일 1 ← "Waterproof"), District Vision 콜라보(1080 v15 · 슈퍼컴프 엘리트 v5). 제외 목록에 `waterproof` · `wp` · `district vision`을 더해 일반 색상으로 바꿨다(이미지가 없어진 행 0).
5. **직전 세대가 StockX에 없을 때:**
   - 그 행은 `review`(`_missing.image = "not_on_stockx"`)로 두고 **적재하지 않는다.**
   - 다른 곳(GOAT · 공식몰) 사진으로 메우지 않는다. 배경과 각도의 통일이 깨지기 때문이다.
   - 몇 개인지 보고하고, 사람이 넣을지 정한다.
6. **현행 세대가 StockX에 없을 때:** 같은 처리다(`review`). 막 나온 세대는 StockX 등록이 늦을 수 있어 9장의 월 1회 확인에서 다시 찾는다.
7. **보조 키:** 고른 결과의 `sku` · `slug`를 중간 파일에 남긴다. 이미지 URL이 바뀌면 `slug`로 다시 조회한다.

### 3.5 직전 세대가 없는 라인

- 첫 세대만 있는 라인(엘립스 v1, 메가블라스트, 엔돌핀 아주라, 하이퍼부스트 등)은 **한 행만** 넣는다(`generation = 1`, `is_current = TRUE`).
- 일부러 빈 자리를 만들지 않는다.
- **직전 세대가 단종돼 공식몰에 없을 때:** 스펙은 웹 검색(리뷰 매체 · 보도자료)으로 찾고 필드마다 출처를 남긴다. 정가는 출시 당시 국내 정가를 찾으면 넣고, 못 찾으면 `null`이다(`partial`).

### 3.6 화면 노출 — 평평하게(설계만, 화면 구현은 이번 범위 밖)

구조로는 라인으로 묶지만 화면에서는 세대마다 **독립된 신발**로 보여 준다.

- **목록 · 검색 · 비교:** 카야노 32와 33이 그냥 나란히 나온다. 라인으로 접거나 묶지 않는다.
- **현행 필터:** `is_current` 필터("현행만")는 두지만 **기본은 전체 노출**이다. 구형을 찾는 사람이 "왜 안 나오지" 하지 않게 한다.
- **상세:** 상세에서만 "이전 세대 / 다음 세대" 링크를 보여 준다. 같은 `line_key`에서 `generation`이 바로 앞 · 뒤인 행이다.
- **리뷰 · 평점 · 찜:** 세대별 신발에 붙는다(8장). 라인 단위로 합산하지 않는다.
- **API(적재 단계에서 같이 바꾼다 — 2026-10-24 로컬 구현 · 계약 검증, 미커밋 · 운영 미반영. `docs/API_CONTRACT.md` 2.3):**
  - 신발 응답에 `lineKey` · `generation` · `isCurrent`를 더한다.
  - 목록에 `?isCurrent=true` 필터, 상세 이웃 세대용 `?lineKey=` 조회를 더한다.
  - 계약 기준선(spring-v3)이 바뀌므로 새 기준선을 만든다.
- **챗봇 · 세대 비교:** `line_key`와 `generation`으로 "32 vs 33"을 찾는다.

## 4. 후보 선정 기준

StockX의 `rank` · `weekly_orders`는 쓰지 않는다. 러닝화는 주간 거래가 거의 0~1이었다.

1. **세대:** 라인마다 **현행 + 직전 1세대**를 넣는다. 2세대 전은 넣지 않는다(재고가 거의 없고 확신도가 낮은 데이터가 늘어난다). 예외는 이미 DB에 있는 행이다(3.2).
2. **라인 범위:** 현행 세대가 있는 로드 · 트레일 러닝 라인이다.
   - GTX 변형과 마이너 브랜드를 더해 수를 채우지 않는다.
   - **트레일은 50개 안팎으로 줄인다**(초안 78 → 50, 부록 B.2).
3. **브랜드별 할당:** 상한으로만 쓴다(아식스 40 · 나이키 35 · 아디다스 35 · 호카 30 · 뉴발란스 30 · 사우코니 25 · 브룩스 20 · 온 20 · 미즈노 20 · 살로몬 15 · 푸마 15 · 알트라 10 · 기타 5). 현행 라인업이 모자라도 채우지 않는다.
4. **용도 · 안정화 최소 비율은 두지 않는다.** 시장의 실제 크기(템포 29 · 안정화 30)를 그대로 받는다.
   - 대표 안정화는 모두 들어간다: GT-2000 · GT-1000 · 젤 카야노 · 아드레날린 GTS · 글리세린 GTS · 860 · 가이드 · 허리케인 · 웨이브 인스파이어 · 아라히 · 가비오타 · 스트럭처 · 슈퍼노바 솔루션.
5. **규모:**
   - 라인 약 240개(초안 265에서 트레일 −28, 확신도 low 정리 뒤 확정)
   - 신발 약 450켤레: 현행 약 240 + 직전 약 210(신규 라인은 직전이 없다)
   - 여기에 기존 행 중 직전 범위 밖의 엔돌핀 스피드 4가 더해진다

**결과물:**
- 후보 목록 `catalog/candidates.csv`: **세대마다 한 행**이다.
- 칸은 `line_key` · `generation` · `is_current` · 브랜드 · 영문 라인 · 한글 표시명 · 용도 · 안정성 · StockX 검색어 · 근거 URL이다.
- 라인 행 하나에서 현행 행과 직전 행이 함께 나오므로 `line_key`는 수집 과정에서 바로 붙는다.

## 5. 이미지 — StockX URL 핫링크

**시험 결과(2026-10-21, 20/20):**
- 20장 모두 네 귀퉁이가 **`#FFFFFF`**다. 배경 인자를 빼도 원본 사진이 흰 배경이다.
- 모두 측면 사진이고 **앞코가 오른쪽**이다(사용자 육안 확인).
- 크롭이 같다. 신발이 가로의 97~99.7%를 채우고, 중심은 (0.49~0.51, 0.49~0.51)이다.
- 외부 Referer(`https://runshoes.ronanlab.dev/`)로 요청해도 **200**이다.
  - 헤더: `cross-origin-resource-policy: cross-origin`, `cache-control: public, max-age=31536000`
- 대표 이미지는 1장이다. 360° 36프레임은 20켤레 중 8켤레에만 있다.

**규칙:**
- **저장하지 않는다.** DB의 `image` · `images`에는 `images.stockx.com` URL만 들어간다. 컨테이너 이미지와 PVC에 신발 사진이 늘지 않는다.
- **크기는 URL 인자로 정한다.** imgix 인자 `w` · `h` · `dpr`를 쓴다.
  - 중간 파일과 DB에는 기준 URL 하나를 둔다: `fit=fill&bg=FFFFFF&trim=color&w=700&h=500&dpr=2&fm=webp&q=90` + StockX가 준 `updated_at`.
  - 화면(카드 · 모달)은 프런트의 작은 함수 하나로 `w` · `h` · `dpr`만 바꿔 요청한다.
  - API가 주는 기본값은 140×100 썸네일이라 그대로 쓰지 않는다.
- **출처 표기:** 이미지 아래에 **"Image: StockX"**를 표시한다. 이미지 URL의 호스트로 판단하므로 컬럼은 필요 없다. 사이트 하단에도 같은 문구와 내리는 방침을 둔다.
- **요청 시 내린다:**
  - 권리자(StockX · 브랜드)가 요청하면 해당 이미지 URL을 지운다. 그 신발은 "이미지 없음" 칸(회색 상자, 같은 비율)으로 바뀐다.
  - 연락처와 처리 기한(영업일 3일 이내)을 하단 고지에 적는다.
  - 요청 기록은 `docs/HISTORY.md`에 남긴다.
- **깨진 링크:** 9장의 월 1회 확인이 모든 이미지 URL에 HEAD를 보낸다. 200이 아니면 `review`로 두고 `slug`로 다시 조회한다.
- **화면 조건:**
  - 지금은 CSP가 없다(2단계에서 넣지 않기로 함). 나중에 CSP를 넣으면 `img-src`에 `https://images.stockx.com`이 있어야 한다.
  - `image`는 `VARCHAR(500)`이다. 기준 URL은 약 200자라 들어간다. **스키마 변경이 없다.**
- **권리 메모:** KicksDB 약관은 "API data"의 캐시 · 재배포를 허용한다. 그러나 제3자 데이터의 소유권은 부인한다. 이미지 권리는 StockX · 브랜드에 있고, 이 방식은 **허락이 아니라 참조**다. 출처 표기와 내리는 방침은 그래서 둔다.

**KicksDB 사용:**
- 무료 플랜(월 1,000회)을 쓴다. 300켤레 × 검색 1~2회면 한 번에 끝난다.
- 키는 로컬 파일(권한 600)이나 환경변수로 둔다. git · 로그에 남기지 않는다.
- 응답에서 쓰는 필드: `image` · `sku` · `slug` · `gender` · `primary_title` · `secondary_title` · `rank` · `gallery_360`(나중에 회전 보기).
- 쓰지 않는 필드: `description`(StockX 글) · 가격(미국 리셀가).

## 6. 표기 규칙과 중간 포맷

### 6.1 표기 규칙 — 지금 20켤레의 방식을 따른다

- **brand:** 한글 고정 목록이다(아식스 · 나이키 · 아디다스 · 호카 · 뉴발란스 · 사우코니 · 브룩스 · 온 · 미즈노 · 살로몬 · 푸마 · 알트라 …). 별칭 표에서만 나온다.
- **model:** **한글 음차 + 세대 숫자**("젤 카야노 32", "엔돌핀 스피드 4", "프레시폼 X 880 v15").
  - 표시명은 **수집한 문자열에서 만들지 않는다.** 별칭 표의 라인별 한글 이름(`ko`)과 세대 표기 형식(`version_format`: `{n}` 또는 `v{n}`)으로만 조립한다. 영문 상품명이 그대로 섞여 들어올 길을 막는다.
  - 검사: model은 `^[가-힣0-9 ·]+( [A-Za-z0-9]+)*$`처럼 한글 · 숫자 · 공백이 기본이다. 라틴 문자는 라인별 허용 낱말(`allow_latin`: 예 880 라인의 `X`, `v`, 아드레날린의 `GTS`)만 된다. 그 밖의 라틴 문자가 있으면 `review`다.
- **midsole:** 브랜드 상표의 **영문 원문**(FF Blast Plus · ZoomX · DNA Loft v3)이다. 기존 20켤레 중 "리액트X" 하나가 이 규칙과 다르다(10장).
- **숫자:** weight는 정수 g(남성 기준 사이즈), drop은 mm, stackHeight는 뒤꿈치 mm(0.5 단위)다. price는 국내 정가(원, 공식몰 → ABC마트 — 2.2.2)다.

### 6.2 중간 포맷 — `catalog/shoes.jsonl`(한 줄에 한 켤레)

DB 컬럼과 1:1에 가깝게 둔다. 추가 키는 적재기가 쓰고 DB에는 넣지 않는다.

```json
{
  "catalog_key": "asics:gel-kayano:32",
  "line_key": "asics:gel-kayano", "generation": 32, "is_current": false,
  "brand": "아식스", "model": "젤 카야노 32",
  "purpose": "조깅·회복주", "stability": "안정화",
  "midsole": "FF Blast Plus Eco",
  "official_weight_g": 298, "official_weight_size": "M9", "official_heel_mm": 40, "official_drop_mm": 8, "official_spec_size": null,
  "measured_weight_g": null, "measured_weight_size": null, "measured_heel_mm": null, "measured_drop_mm": null, "measured_source": null, "measured_count": null,
  "width": "보통", "wideAvailable": true, "carbon": false, "price": 199000,
  "summary": "…", "description": "…",

  "sku": "1011C284-400", "slug": "asics-gel-kayano-32-sunny-sizzle",
  "images": [{"url": "https://images.stockx.com/images/…?fit=fill&bg=FFFFFF&w=700&h=500&…", "source": "stockx"}],
  "sources": {"official_weight_g": "https://…", "official_drop_mm": "https://…", "official_heel_mm": "https://…", "price": "https://…", "midsole": "https://…"},
  "status": "ok",
  "_missing": {},
  "checked_at": "2026-10-21"
}
```

- **DB에 가는 것:** 위 첫 묶음의 필드(`line_key` · `generation` · `is_current` · `official_*` · `measured_*`는 V4 컬럼). V5 전까지는 옛 컬럼(`weight` · `drop_mm` · `stack_height`)에도 공시값을 같이 쓴다 — 옛 이미지로 롤백해도 같은 값이 보이게. 그리고 `image = images[0].url`, `images = images[].url`. rating · reviewCount · likeCount · liked는 넣지 않는다(서버가 계산한다).
- **status:**
  - `ok`: 다 있음
  - `partial`: 적재 최소 조건은 넘었고 일부가 공표되지 않음. `_missing`에 `{"stackHeight": "not_published"}`처럼 남긴다
  - `review`: 사람이 볼 것. 범위 밖 값, 출처 간 불일치, 매칭 애매, 표기 검사 실패
  - `failed`: 받기 · 읽기 실패
  - **`ok` · `partial`만 적재한다.**
- **적재 최소 조건:**
  - brand · model · purpose · stability · width · wideAvailable · carbon이 모두 있어야 한다.
  - 공시 무게 · 드롭 · 힐 스택 3개 중 2개 이상이 있어야 한다(2026-10-24 사용자 — 정가는 소스가 막혀 못 채우는 필드라 적재를 막지 않는다. 이 기준으로 20행이 적재 대상이 됐다).
  - **비어도 막지 않는 칸(2026-10-24 사용자):** 발볼 · 와이드 · **카본**. 카본은 출처 면제 항목이라 비었다고(null) 또는 출처 감사에서 떨어졌다고 적재를 막지 않는다(화면은 "정보 없음"). 이 기준을 고치자 카본만 비어 빠져 있던 15행이 적재 대상이 됐다. V4 가 `carbon` 도 NULL 을 허용한다.
  - 사람 판단 `review`(값을 두되 다시 볼 때까지 적재하지 않음)와 `clear`(어느 칸이든 비움)를 `decisions.json`에 쓸 수 있다.
  - 이미지가 1장 이상 있어야 한다.
  - 값마다 `sources` URL이 있어야 한다.
- **범위 검사:** 무게 120~450g · 드롭 0~14mm · 스택 15~50mm · 정가 1만~60만 원(하한 2026-10-28 사용자)을 벗어나면 `review`다.

```

  README.md                 흐름 · 실행법 · 사람이 보는 단계
  sources.yaml              도메인별 robots · 약관 확인 날짜 · 방식(fetch | manual)
  aliases.yaml              브랜드 · 라인 별칭, 한글 이름, 세대 형식, 허용 라틴 낱말, StockX 검색어
  candidates.csv            승인된 후보 300(4장)
  shoes.jsonl               적재 대상(6.2)
  normalize.mjs  validate.mjs  stockx.mjs  load.mjs  report.mjs
catalog/local/              ← .gitignore
  adapters/<도메인>.mjs      공식몰 스펙 수집기
  cache/                    받은 원본 HTML · KicksDB 응답
```

- 공개되는 것: 사실 수치 · 상표명 · 우리가 쓴 글 · 출처 URL · 이미지 URL. 남의 글 · 사진 파일 · 원본 HTML은 공개하지 않는다.
- 도구는 Node(`.mjs`)다(`contract/`와 같다).
- **적재 경로: `shoes.jsonl` → 적재기 → 관리자 API.**
  - 앱 검증을 그대로 탄다. PR diff로 검수한다. 계약 시드(V2의 20켤레)에는 손대지 않는다.
  - 적재기는 `GET /api/shoes`로 지금 목록을 받고 `catalog_key`로 비교한다.
    - 없으면 `POST`(id는 앱이 max+1로 매긴다)
    - 사실 값이 다르면 `PATCH`
    - 같으면 건너뛴다
  - **기본은 건조 실행**이다. `--apply`를 붙여야 쓴다. 구현은 `catalog/load.mjs`(계획은 `local/work/load-plan.json`). 시드 20켤레는 사실 값만 PATCH하고 이미지 · 요약 · 설명은 건드리지 않는다.
  - 운영에는 30 → 100 → 300 순서로 넣는다. `/api/shoes`는 페이지 없이 전부 돌려준다. 300켤레면 약 450KB이고, 첫 30켤레에서 화면과 응답 크기를 본다.
  - 넣은 id를 `catalog/loads/<시각>.json`(gitignore — 운영 기록은 런북의 덤프 폴더에)에 남겨 `--revert`할 수 있게 한다. 리뷰가 붙기 전까지만 깔끔하게 되돌릴 수 있다.
  - 시드 20켤레의 요약 · 설명은 `copy.json` 에 `seed_choice`(사용자가 원본 · 재작성 중 고른 것)가 있을 때만 PATCH 한다(2026-10-29). 그 전 V4 전 DB(시드에 lineKey 없음)에는 돌지 않는다 — 시드를 새 행으로 또 넣기 때문(exit 2). 운영은 `--base http://192.168.122.240 --host runshoes.ronanlab.dev`.

### 7.1 관리 화면 수정 보호(2026-10-29 사용자 — "진짜 관리자가 고친 값이 적재 때 되돌아가면 안 된다")

적재기는 카탈로그가 정답이라 운영 값이 다르면 되돌린다. 사람이 관리 화면에서 고친 값이 그렇게 사라지지 않게:

1. **스냅숏** — `load.mjs --apply` 가 끝나면 그 직후의 운영 값을 `catalog/local/work/snapshot-<호스트>.json` 에 둔다(`--snapshot` 은 적재 없이 적기만). 칸 목록은 `catalog/live-fields.mjs`(사실 값 + 용도 · 문구 · 이미지)
2. **알아보기** — 스냅숏과 지금 운영 값이 다른 칸 = 관리 화면에서 고친 칸. 데모 관리자는 서버가 쓰기를 막으니 진짜 관리자 계정의 수정이다
3. **저절로 가져오기** — `--apply` 는 적재 전에 `pull-admin.mjs --write` 를 부르고, 옮긴 것이 있으면 `build.mjs` 를 다시 돌린 뒤 진행한다(2026-10-30 사용자 — 멈추지 말고 끌어와서 진행, CronJob 은 나중에).
   - 로그: 화면에 `어드민 수정 N건을 decisions.json에 반영했다` + 칸마다 `<catalog_key> <필드>: 전 → 후`(문구는 `(copy.json)`). 같은 내용이 `loads/<시각>.json` 의 `adminPulled` 에(바꿀 것이 없어도 파일을 남긴다), 마지막 실행은 `local/work/pull-admin-last.json`
   - 건조 실행은 `pull-admin.mjs` 를 쓰지 않고 돌려 `적용하면 어드민 수정 N건을 … 반영한다` 만 낸다
   - 멈추는 것은 **관리 화면에서 새로 넣은 신발(구조 변경)** 뿐이다(2026-10-30 사용자). 후보 목록에 넣을지 정한 뒤 `--structure-ok` 로 진행한다(exit 3)
   - 관리 화면의 삭제는 숨김(V8)이다 — 숨긴 신발은 `decisions.json` rows.hidden(`action: "hide"`)으로 옮겨 빌드가 적재 대상에서 빼고(status `hidden`), 되살리면 `show` 로 바꾼다. 멈추지 않는다. 그래도 숨긴 신발을 POST 하려 하면 멈춘다
   - V6 전 앱(응답에 `specSources` 가 없다)에는 `--apply` 하지 않는다(exit 2) — 건조 실행은 된다
   - 끌어온 뒤에도 되돌릴 칸이 남으면(빈틈) 멈춘다. 스냅숏이 없으면 `--apply` 하지 않는다(`--no-snapshot-ok` 는 처음 한 번만)
4. **가져오기 규칙** — `node pull-admin.mjs [--base … --host …] --write` 로 따로 돌려도 된다(운영은 읽기만):
   - 스펙(중량 · 중량 사이즈 · 드롭 · 스택하이트 · 미드솔 · 발볼 · 와이드 · 카본) · 가격(+출처 · 날짜 · 종류) → `decisions.json` rows, `by: "user"`, `via: "admin"`, 출처 `manual`(MAN). 비운 칸은 `clear`
   - 브랜드 · 모델명 · 안정성 · 현행 → `decisions.json` rows(빌드가 후보 목록 값을 덮는다)
   - 요약 · 설명 → `copy.json`(시드면 `seed_choice: "admin"`), 대표 · 추가 이미지 → `image_overrides`(`via: "admin"` 이면 빌드가 둘 다 그대로 낸다)
   - 라인키 · 세대 · 성별 · 실측(무게 · 사이즈 · 출처 · 횟수 · 스택 · 드롭) · 스펙 기준 사이즈 → `decisions.json` rows(2026-10-30 사용자 — 관리 화면 수정은 전부 의도한 수정)
   - 스펙 출처(V6 `specSources`) → `decisions.json` rows.spec_sources(빌드가 `shoes.jsonl` 의 `spec_sources` 로 낸다). 관리 화면에서 고른 출처에 주소가 있으면 그 칸의 판단 `source` 도 그 주소(없으면 `manual`)
     - 라인키 · 세대를 바꾸면 `shoes.jsonl` 의 `catalog_key`(운영 행을 찾는 키)만 바뀌고, 판단 · 문구를 찾는 키 `source_key`(후보 목록 키)는 그대로다. 빌드는 `catalog_key` 가 겹치면 멈춘다
   - 카탈로그 밖 시드(엔돌핀 스피드 4): 이미지 → `seed_only_images`, 가격 출처 → `seed_only_price_meta`, 문구 → `copy.json`. 나머지 칸은 적재기가 덮지 않아 로그에만 남긴다
   - 새로 넣은 신발 → 옮기지 않는다(구조 변경, 위 3). 숨긴 · 되살린 신발 → rows.hidden(위 3)
   - 같은 스냅숏으로 다시 돌려도 같은 판단을 두 번 쓰지 않는다
5. 적재가 끝나면 스냅숏이 새로 적힌다 — 다음 적재는 그 뒤의 수정만 본다

## 8. 생성 단계 — 글과 리뷰(이번 범위 밖, 순서만 정함)

신발을 적재한 다음에 한다.

- **summary · description:** 스펙과 편집 값으로 만든 우리 글이다. 수집한 글을 옮기지 않는다.
  - 세대 사이의 차이(미드솔 · 무게 · 스택 변화)는 두 행의 사실 값에서 나온다.
- **리뷰:** **세대별 신발에 단다**(라인이 아니라 `shoes.id`).
  - 미드솔이 바뀌면 다른 신발이다. "32는 좋았는데 33은 별로"가 표현돼야 한다.
  - 규모는 약 450켤레에 **2,500~3,000건**, 신발마다 0~10건을 차등으로 붙인다.
    - 리뷰 0건인 신발도 있다. 평점은 서버가 리뷰로 계산하므로 0이 된다.
  - 같은 사용자가 두 세대를 모두 리뷰하면 세대 비교가 자연스러워진다.
  - 작성자는 시드 사용자 30명이다. V3 제약은 한 사람이 한 신발에 첫 리뷰 하나다. 그래서 신발당 최대 30건이고, 10건 상한과 충돌하지 않는다.
  - 쓰는 경로는 신발 적재와 같다(중간 파일 → 적재기 → API, 건조 실행 기본). createdAt은 서버 시각이라, 날짜를 흩뜨리려면 적재 방식을 따로 정해야 한다.
- **생성 수단:** 정하지 않았다. Ollama · GPU는 지금 쓸 수 없다(다른 프로젝트가 학습 중).

## 11. 수집 · 검증 규칙(2026-10-21 확정)

수집하면서 정한 규칙이다. 코드가 강제하는 것은 파일 이름을 적었다.

1. **기본값으로 메우지 않는다.** 어떤 필드든 값을 못 구하면 `null`이다.
   - 발볼 '보통' · 와이드 false · 카본(후보 초안 값)을 기본값으로 넣었다가 결손률이 가려진 일이 있었다.
   - 그래서 V4에서 `width` · `wide_available`을 NULL 허용으로 바꿨다. 화면은 NULL을 "정보 없음"으로 보인다.
2. **주소를 지어내지 않는다.** 매체 · 보도자료 페이지는 사이트맵 색인(`local/work/media-index.txt`, `press-index.txt`)이나 검색 결과(`search-urls.txt`)에 있는 주소만 읽는다(`local/fetch.mjs`가 거절). sitemap 자체는 읽어도 된다.
3. **허용 호스트만 읽는다.** `sources.yaml` · `sources-media.yaml`에서 `mode: fetch`인 호스트만 읽는다. 나이키 · 알트라 글로벌 · 리닝 · 엑스텝은 코드에서 막는다. robots를 지키고, 호스트마다 5초 간격(프로세스를 넘어서), 403 · 418 · 429면 멈춘다. 리다이렉트도 홉마다 호스트를 검사한다.
4. **출처 감사**(`audit.mjs`) — 필드마다 다음을 확인한다.
   - 주소가 색인에 있는가
   - 실제로 200으로 받았는가
   - 값이 그 페이지 본문에 있는가. 미드솔은 표기 차이(™ · + · FlyteFoam)를 맞춰 보고, 스택 · 드롭은 ±0.5mm까지 같은 값으로 본다
   - 같은 세대의 페이지인가
   - 숫자는 단위와 함께 있어야 페이지에 있는 것으로 본다(`39.5 mm` · `173 g` · `6.1 oz`, 또는 표의 라벨 `Weight (g) 323` · `Drop (mm) 11`). 단위 없는 같은 숫자(평점 · 가격)로는 통과하지 않는다.
   - 못 넘으면 출처를 떼고 review로 보낸다. 감사 결과는 파일 · 행마다 따로 적용한다.
5. **무게는 US M9 기준이다.**
   - 값은 `official_weight_g`, 그 무게의 기준 사이즈는 `official_weight_size`(`M9` · `M10.5` · `W7.5`, 출처가 밝히지 않으면 `null`)다.
   - 다른 사이즈로 밝힌 값은 그 사이즈 라벨을 달아 두고, M9 값을 찾으면 바꾼다. 비교 화면은 M9끼리만 나란히 그린다.
   - oz만 적힌 무게는 g로 환산해 쓴다(×28.35, 반올림 — 2026-10-23 사용자: Adios Pro 5 "6.1 oz" = 173g). 사이즈 표기가 없으면 기준 사이즈는 `null`이다.
   - 남성 UK 8 = US M9로 본다(푸마 국내 공식몰 "UK 8 사이즈 기준", 보도자료 "UK8 (M)").
   - 여성 US W7 무게는 이미 읽은 페이지에서 보이면 기록만 한다(`local/work/women-weights.json`).
6. **와이드:**
   - `true`는 출처 페이지에 와이드 판이 나온다는 문장이 있을 때다(`extract-fit.mjs`). 그 모델 · 세대 리뷰(BITR · RSG)의 본문만 읽는다.
     - 낱말 "2E" · "와이드"만으로는 잡지 않는다(2026-10-23, true 17건 오염): 몰 메뉴("옴니9 와이드"가 사우코니 12행), 리뷰어 자기 신발("my 10.5 2E"), "regular and wide" 발 이야기, 부정문("doesn't come in a wide version" — 정반대 뜻), 독자 댓글("… says: December 21, 2022"부터는 읽지 않는다), 다른 모델 · 다른 세대 페이지.
   - `false`는 아래 경우만이다. 침묵으로 증명하지 않는다.
     - **국내 공식몰 라인업에 와이드가 없다는 것은 근거가 아니다**(2026-10-24 사용자 정정). 국내 라인업은 글로벌 라인업의 일부라, 국내 유통사가 들여놓지 않았을 뿐일 수 있다. 실제로 웨이브 라이더 29는 국내몰에 와이드가 없어도 미즈노 미국 공식몰에 Wide 2E(Style #411537)가 있다. 이 규칙으로 넣었던 false 23행을 비웠다. `wide-store.mjs`는 true(국내몰에 와이드 상품이 있음)만 낸다.
     - 브랜드 **글로벌** 라인업에 그 세대가 있는데 와이드가 없다고 확인한 경우(사람 · 웹 검색 판단, `decisions.json`).
     - 그 모델 · 세대 리뷰의 "no wide" 명시(2026-10-23 사용자 승인, `local/work/wide-no.jsonl`). 때를 한정한 말("yet" · "currently" · "for now" · "at launch")은 뒤에 와이드가 나올 수 있어 쓰지 않는다. 같은 행에 true 근거가 있으면 비운다.
     - 웹 검색: 브랜드 1곳 또는 서로 다른 도메인 2곳이 같은 쪽이고, 반대 읽기가 하나도 없을 때.
   - 쓰지 않는 것: 소매점의 사이즈 · 폭 선택(재고와 구분되지 않는다), 구매자 후기 · 포럼 · 댓글, 레이싱화 같은 범주 추정(슈퍼컴프 엘리트 v6 · 디비에이트 니트로 4는 와이드가 있다).
   - 글로벌 공식 페이지의 폭 선택자: 사우코니는 Access Agreement가 데이터 마이닝 · 스크래핑 도구를 금지하고, 브룩스 · 뉴발란스는 약관 페이지부터 403(봇 차단)이라 쓰지 않는다(2026-10-23).
   - **비면 비운 채로 간다**(2026-10-23 사용자). 와이드는 확인 가능한 범위가 구조적으로 좁다. 화면은 "정보 없음"으로 보이고, 챗봇은 모른다고 답한다(화면 · 챗봇 구현 때 반영).
7. **발볼은 토박스 너비다**(V4 `toebox_width`, 2026-10-23). 근거는 리뷰의 토박스 · 포어풋 서술뿐이다 — 미드풋은 끈으로 조절되고, 힐은 발볼과 무관하다(힐 슬립 문제).
   - 쓰지 않는 것: 미드풋 · 힐 · 전체 핏("snug fit" · "narrow last"), 와이드 판 이야기(→ 와이드), 바닥 · 플랫폼("wide forefoot base"), RSG 테스터 표, 리뷰어 자기 발("my wide forefoot"), 다른 신발 이야기.
   - 제안값과 근거 인용은 `local/width.csv`(인용은 공개하지 않는다). 근거가 한 종류(좁음 · 보통 · 넓음)뿐이면 fill이 채우고, 여러 종류면 사람 목록에 올린다. 수집 에이전트가 적은 발볼과 기존 DB(다나와) 발볼은 쓰지 않는다.
   - **근거 수는 비대칭이다(2026-10-24 사용자):** 리뷰 본문(BITR · RSG가 그 모델을 직접 리뷰한 문장)은 1곳이면 된다. 웹 검색은 브랜드 1곳 또는 서로 다른 비실측 도메인 2곳이 일치해야 한다. 소매점 상품 설명은 브랜드 문구를 옮겨 실은 것이라 **여러 곳이어도 1곳으로 센다**.
   - **제외 필터는 두 근거에 같다**(`catalog/toebox-filter.mjs`): 표 라벨 · 비교급 · 질문 · 조건문으로 시작하는 절 · 리뷰어의 발이나 습관 이야기("as someone who runs in wide toeboxes") · "rear of the forefoot". 본문 인용은 창이라 토박스 · 포어풋 낱말이 든 절만 잘라 본다. 이 정리로 익스피리언스 플로우 2(리뷰어 습관), 소매점 문구뿐인 4행(허리케인 25 · 클라우드플로우 5 · 패러다임 8 · 프로비전 8), Marathon Sports 근거를 빼면 1곳만 남는 고스트 맥스 4를 비웠다.
   - 와이드(`wide_available`)는 별개다: 국내 공식몰 라인업의 남성 2E · 4E · 와이드 상품(`wide-store.mjs`, 여성 전용은 보지 않는다), 리뷰의 "available in wide", 웹 검색. 다른 출처가 true면 국내몰에 없다는 것만으로 false로 두지 않는다.
8. **카본은 출처 URL을 요구하지 않는다**(예/아니오, 모델 · 용도로 거의 정해진다). 수동 입력이면 `sources.carbon = 'manual'`이다. 무게 · 드롭 · 스택 · 미드솔은 출처가 필수다.
9. **범위:** 무게 80~400g · 드롭 0~14mm · 스택 10~65mm를 벗어나면 review다(맥시멀 신발은 61mm, 레이싱 플랫은 20mm 아래도 있다).
10. **사람의 판단은 `decisions.json`에 남기고 수집값보다 먼저 적용한다.**
    - keep_db: 기존 값 유지
    - use_source: 출처 값으로 바꾼다
    - clear: 비운다
    - 기존 20켤레의 정가는 비운다. 다나와는 쓰지 않는다.
11. **사람이 채우는 목록과 순서(이전 방식 — 14로 대체):** `decide.csv` → `carbon.csv` → `weight.csv` → `local/width.csv` → `rest.csv`(`split-tasks.mjs`가 만든다). 사람이 넣은 값도 같은 감사 · 범위 검사를 거친다. 다만 사람이 넣은 출처 URL은 우리가 페이지를 읽지 않았으므로 기록만 한다.
12. **스펙은 제조사 공시값이다**(V4 `official_*`). 실측값 칸(`measured_*`)은 사람이 `decisions.json`의 `measured_weight_g`(`{value, size, source}`)에 적은 것만 채운다 — 공식값과 리뷰 무게(BITR의 M10 · M10.5 등)가 다를 때 둘 다 둔다(2026-10-23 사용자). 어느 쪽을 화면에 쓸지는 비교 페이지에서 정한다. 공식값과 같은 리뷰 무게는 공식값으로 통일하고, 공식 출처가 사이즈를 적지 않았으면 그 값을 사이즈와 함께 적은 리뷰의 라벨을 쓴다. RunRepeat 같은 유료 실측은 넣지 않는다.
    - **출처 우선순위:** 공식(STORE 국내 공식몰 · PR 보도자료) → BITR 상자 → F2R(fit2run 스펙 블록) → RSG 상자 → BITR 본문 → RSG 본문(`fill.mjs`). F2R은 소매점이 브랜드 스펙을 옮겨 싣는 것이라 사이즈 표기를 함께 주는 BITR 상자보다 뒤, RSG 상자보다 앞이다 — RSG 스택은 Running Warehouse 실측과 같은 값이 여러 번 나왔다(2026-10-24).
    - WEB · MAN(사람이 웹 검색 · 직접 확인으로 정한 값, `decisions.json`)은 순위 밖이다. 사람이 정했거나 붙잡아 둔 필드(keep_db · use_source · hold · flag)는 다시 고르지 않는다.
    - 무게는 US M9가 먼저다: M9로 확인된 값 → 다른 사이즈로 밝힌 값 → 사이즈 불명 값, 각 묶음 안에서 위 우선순위.
    - 스택 · 드롭은 제조사 발표값이다. 기준 사이즈(`official_spec_size`)는 제조사가 밝히지 않아 대부분 `null`이다. M9라고 단정하지 않고, 사이즈로 보정하지 않는다(2026-10-23 대조: BITR M10.5 페이지 4/4가 공식값과 같음).
    - 포어풋 스택은 두지 않는다(힐 − 드롭). 출처가 셋을 다 적었으면 힐 − 드롭 = 포어풋(±0.5)인지 본다(`check-forefoot.mjs` → `forefoot-check.csv`).
    - 미드솔은 상자에서 읽지 않는다(BITR Key Features는 자유 문장). 상자 안에서 oz와 g가 안 맞으면(±5%) 버린다. RSG의 `999`는 값 없음이다.
    - 다른 판 · 다른 모델 · 모음 글은 모든 필드에서 쓰지 않는다(`variant.mjs`, 스펙 상자 · 감사 · 발볼 근거가 같이 쓴다). 주소에 라인 이름에 없는 변형 낱말(GRVL · GTX · Hike · Wide · Mid · Max · GTS · ATR · Low · Lightspray · Evo · Ultra · Elite · Plus · Trail)이 있거나, `best-…` · `…-vs-…` 같은 모음 · 비교 글이거나, 라인 낱말이 하나도 없으면 다른 신발이다. 공식 이름에 붙은 낱말(Challenger ATR 7)과 제목으로 확인한 주소는 예외다. 와이드 판 페이지는 와이드 판 근거로는 쓴다.
    - **solereview는 소스에서 뺀다**(2026-10-23, `sources-media.yaml` `mode: excluded`). 반 켤레를 직접 달고 스택도 재는 실측이라 공시값이 아니다. 거기서 온 값은 지우고 다른 출처로 채운다. 카본은 출처 면제라 값은 두고 출처만 뗀다. `decisions.json`의 사람 판단은 출처가 solereview여도 그대로 둔다.
    - **기존 DB(다나와) 값의 상당수는 Running Warehouse 자체 측정치다**(2026-10-23 웹 검색으로 확인: 보스턴 13 스택 37 · 슈퍼노바 라이즈 3 무게 264 · 스택 36 · 베이퍼플라이 4 무게 167이 Running Warehouse가 직접 잰 값과 같았다). 기준 불명이 아니라 실측이라 쓰지 않는다. **DB 값이 Running Warehouse 값과 같으면 실측으로 본다.** 공식값이 확인된 필드만 DB 값을 남기거나 되돌린다(님버스 27 스택 43.5 · 880 v15 스택 40.5 · 스피드크로스 6 스택 32는 공식값과 같았다).
    - **웹 검색(WEB) 근거 기준:** 브랜드 공식 페이지 · 보도자료 1곳, 또는 실측이 아닌 서로 다른 도메인 2곳 이상이 같은 값일 때만 판정한다. 제조사 스펙을 그대로 싣는 소매점 기술표(REI · Fleet Feet · Marathon Sports 등)와 그 스펙을 인용한 리뷰는 근거가 된다. 실측(RunRepeat · RTINGS · Running Warehouse 자체 측정 · Doctors of Running · solereview, "we measured" · "my size 10 weighs" 류)은 근거에서 뺀다. 판정 못 하면 확인 불가로 두고 값은 그대로 둔다. Claude가 검색한 판단은 `decisions.json`에 `via: web, by: claude`로 사람 판단과 구분한다.
    - 기존 20켤레는 DB 값을 바꾸지 않고, 다르면 사람 목록에 올린다. 출처 URL은 그 페이지에 같은 값이 있을 때만 DB 값에 단다 — 0.5 차이도 다른 값이다(님버스 27: DB 43.5 · BITR 44).
13. **남녀는 별도 행이다**(V4 `gender`, `UNIQUE (line_key, generation, gender)`, 기존 20켤레는 `men`). 여성 무게 기준은 US W7.5다.
    - 여성 스택 · 드롭은 허용 출처에 거의 없다. 스펙 상자 15행이 남성과 같은 값이었고, 1단계 공식몰은 푸마 · 살로몬만 텍스트로 적는다(최대 약 30행).
    - 그래서 여성 행은 보류한다(50행 미만이면 보류 — 사용자). 남성 값을 빌려 오지 않는다.
14. **사람이 채우는 파일은 하나**(`todo.csv`, `todo.mjs`가 만든다): 신발 하나가 한 줄(`line_key` + `generation`)이다.
    - 출처는 약자로 적는다: BITR believeintherun.com · RSG runningshoesguru.com · STORE 브랜드 국내 공식몰 · PR 보도자료 · WEB 웹 검색(사람이 Claude로 찾음, URL 있음) · MAN 사람이 직접 확인 · DB 기존 DB(다나와) · SX StockX(이미지). 실제 URL은 `todo-sources.csv`에 있다. 사람 판단에 남은 solereview만 SOLE로 보인다.
    - WEB과 MAN은 `decisions.json`의 `via`(`web` | `manual`)로 가른다. WEB의 URL은 사람이 찾은 것이라 fetch로 다시 읽지 않는다.
    - 기존 20켤레의 DB 값(DB, 다나와 입력 · 측정 기준 없음)은 적재를 막지 않는다. 운영 값이라 적재가 바꾸지 않는다. 출처 페이지 값과 0.5 넘게 다르면 `todo.csv`에 충돌로 올린다. 그 페이지 URL을 DB 값에 달지 않는다.
