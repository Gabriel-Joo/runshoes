#### 0. 한 줄 요약

카탈로그(`shoes.jsonl`)를 **관리자 API 로** 운영에 넣는 적재기다. 기본은 건조 실행이고, 쓰기 전에 **관리 화면에서 사람이 고친 값을 먼저 판단으로 옮겨** 되돌리지 않는다. 사람 판단은 `decisions.json` 에 남고 수집값보다 먼저 적용된다.

#### 1. 최종 설계

#### 1-1. 흐름

```
candidates.csv ─ 수집기들(local/work/specs-*.jsonl · fit2run · ABC마트 · 국내몰) ─ fill.mjs(출처 순위) · audit.mjs(출처 감사)
     │
     ▼
build.mjs ← decisions.json(사람 판단) · copy.json(요약 · 설명) · extra-images.json(색상) · KicksDB 캐시(대표 이미지 · 품번)
     │
     ▼
shoes.jsonl(408행, 상태 ok · partial 만 적재 대상 301) ─ load.mjs ─ 관리자 API(/api/shoes) ─ 운영 DB
```

- **적재 경로는 앱의 관리자 API 다.** DB 에 직접 쓰지 않는다 — 앱 검증(값 범위 · 출처 형식 · 품번 형식)을 그대로 탄다.
- 운영 행은 `lineKey + generation` 으로 맞춘다. 없으면 POST(id 는 DB 가 매긴다), 사실 값이 다르면 PATCH, 같으면 건너뛴다. 비교하는 칸은 `live-fields.mjs FACTS`(스펙 · 가격 메타 · 세대 · 스펙 출처 · 품번 · 와이드 범위).
- 적재기의 요청에는 `X-Runshoes-Client: loader` 를 붙인다. 서버는 적재기의 등록 · 수정에 **수정 시각 · 바뀐 칸(V11)을 찍지 않는다** — 관리 화면의 "최근 수정순"이 사람의 수정만 보이게.
- 운영 행의 `purpose`(용도)는 사람이 검수한 분류라 덮지 않는다. 시드 20켤레의 요약 · 설명은 사람이 고른 것(`copy.json seed_choice`)만 쓴다.

#### 1-2. 사람 판단 — `decisions.json`

- 행 키는 `line_key#generation`, 칸마다 판단 하나.

| action | 뜻 |
|---|---|
| `use_source` | 이 값 · 이 출처로 바꾼다(599칸) |
| `keep_db` | 시드의 기존 값을 유지한다(8) |
| `clear` | 비운다(5) |
| `resolve_official` | 충돌을 공식값으로 정리했다(3) |
| `flag` · `hold` | 값은 두고 사람이 다시 본다(2) |
| `review` | 다시 볼 때까지 적재하지 않는다 |
| `accept_image` | 판정이 애매한 이미지를 받아들인다(1) |

- `by`(user · claude)와 `via`(web · manual · admin · abcmart)로 누가 어떻게 정했는지 남긴다. 지금 Claude 웹 검색 458 · 관리 화면 43 · 사람 승인 27 · 직접 확인 22 · 그 밖.
- 고칠 때 이전 판단을 `previous` 에, 이미지를 바꿀 때 이전 대표를 `was` 에 남긴다.
- 같은 파일에 `image_overrides`(이미지, `01b`) · `hidden` · `purged`(숨김 · 영구 삭제) · 시드 전용 값이 있다.

#### 1-3. 관리 화면 수정 보호(2026-10-29 사용자 — "진짜 관리자가 고친 값이 적재 때 되돌아가면 안 된다")

1. **스냅숏** — 적재가 끝나면 그 직후의 운영 값을 `local/work/snapshot-<호스트>.json` 에 둔다. **한 행을 쓸 때마다 그 행을 스냅숏에 바로 반영한다** — 적재가 중간에 끊겨도 적재기가 쓴 값이 "사람의 수정"으로 보이지 않게.
2. **알아보기** — 스냅숏과 지금 운영 값이 다른 칸 = 관리 화면에서 고친 칸. 데모 관리자는 서버가 쓰기를 막으니 진짜 관리자의 수정이다.
3. **저절로 가져오기** — `--apply` 는 쓰기 전에 `pull-admin.mjs --write` 로 그 칸을 판단으로 옮기고 `build.mjs` 를 다시 돌린 뒤 진행한다(2026-10-30 사용자 — 멈추지 말고 끌어와서 진행). 로그에 `어드민 수정 N건을 decisions.json에 반영했다` 와 칸마다 전 → 후.
   - 스펙 · 가격 · 세대 · 현행 · 성별 · 실측 · 스펙 출처 · 품번 · 와이드 범위 → `decisions.json rows`(`by: user`, `via: admin`)
   - 요약 · 설명 → `copy.json`, 대표 · 목록 이미지 → `image_overrides`(`via: admin`)
   - 숨김 · 되살리기 → `rows.hidden`, 영구 삭제 → `rows.purged`(다시 넣지 않는다)
4. **멈추는 것**(`--apply` 만, exit 3): 관리 화면에서 **새로 넣은 신발**(후보 목록에 넣을지 사람이 정한 뒤 `--structure-ok`), 숨긴 신발을 다시 넣으려 할 때, 끌어온 뒤에도 되돌릴 칸이 남을 때, 스냅숏이 없을 때.
5. 앱이 그 칸을 모르는 옛 버전이면(V4 · V6 · V11 전) `--apply` 하지 않는다(exit 2).

#### 1-4. 운영 적재 — `scripts/load-prod.sh`

```
scripts/load-prod.sh            # 건조 실행 — 비밀번호를 읽지 않는다
scripts/load-prod.sh --apply    # 적용
```

- 운영 VIP · Host 를 정해 두고(`--base` · `--host` 를 넘기면 거절한다), 그 밖의 인자(`--only` · `--revert` …)는 `load.mjs` 로 넘긴다.
- `--apply` 때만 관리자 비밀번호를 Kubernetes Secret `runshoes-auth` 에서 **스크립트 안의 변수로만** 읽는다 — 명령줄 · 출력에 나오지 않고, 적재가 끝나면 지운다.
- 끝나면 적재 기록(`catalog/loads/<시각>.json` — 넣은 id · 바꾸기 전 값 · 끌어온 수정)을 `~/k8s-cluster/backup/<날짜>-runshoes-load/`(권한 600)에 두고, 다시 건조 실행해 0건인지 보인다.
- `--revert loads/<시각>.json` 으로 되돌린다 — 리뷰가 붙기 전까지만 깔끔하다.
- Claude Code 에서는 이 스크립트만 허용 규칙(`.claude/settings.local.json`, 커밋하지 않음)으로 실행한다.

#### 2. 왜 이렇게 했나

#### 2-1. 카탈로그가 정답이되, 사람의 수정이 이긴다

카탈로그는 출처가 붙은 판단의 모음이라 운영과 다르면 되돌리는 것이 기본이다. 그런데 관리 화면은 실제로 쓰는 화면이고, 관리자가 거기서 고친 값(크림 발매가 · 대표 사진 순서 · 이름 표기)은 카탈로그보다 새로운 판단이다. 둘을 같이 살리려면 "누가 고쳤나"를 알아야 하고, 그것을 운영 DB 에 칸마다 저장하는 대신 **적재 직후 스냅숏과의 차이**로 알아본다 — 스키마를 바꾸지 않고 된다.

#### 2-2. 관리자 API 로만 쓴다

DB 에 직접 쓰면 빠르지만 앱의 검증을 건너뛰고, 앱이 계산하는 값(평점 · 찜)과 어긋날 수 있다. API 로 쓰면 관리 화면과 같은 규칙을 탄다.

#### 2-3. 적재기의 수정은 이력에 남기지 않는다

300켤레를 한 번 적재하면 전부 "최근 수정"이 된다. 관리 화면의 수정 이력은 사람이 무엇을 고쳤는지 추적하는 용도라, 적재기 수정은 빼야 의미가 있다.

#### 2-4. 기본은 건조 실행 · 비밀은 명령줄 밖

운영 쓰기는 되돌리기 어렵다. 무엇이 바뀌는지 먼저 보이고, 칸 종류가 예상과 다르면 멈춘다(실제로 여러 번 사람의 수정을 여기서 찾았다). 비밀번호를 명령줄에 두면 셸 기록 · 프로세스 목록 · 권한 판단기에 노출된다.

#### 3. 시도했던 것들

- **적재 순서 30 → 100 → 300(2026-10-28 · 10-29).** 첫 30켤레에서 화면과 응답 크기(300켤레 약 450KB)를 보고 늘렸다.
- **사람의 수정이 되돌아갈 뻔했다 → 스냅숏을 만들었다(10-29).** 처음 설계는 카탈로그가 늘 정답이었다. 관리 화면이 생기자 사람이 고친 값을 적재가 덮을 수 있었다. 처음엔 사람 수정을 찾으면 멈추게(exit 3) 했고, 이튿날 "멈추지 말고 끌어와서 진행"으로 바꿨다(10-30 사용자).
- **덤프로 DB 를 되돌렸더니 96칸이 사람의 수정으로 끌려왔다(10-30, 로컬).** 되돌린 DB 와 적재 직후 스냅숏의 차이를 가져오기가 "관리 화면 수정"으로 읽었다. 판단 파일을 되돌리고 규칙을 적었다 — DB 를 되돌리면 스냅숏도 맞춘다(`--snapshot`).
- **끊긴 적재 뒤 적재기의 쓰기가 사람의 수정처럼 보였다(V11 리허설).** 스냅숏을 적재가 끝날 때만 적어서, 중간에 끊기면 이미 쓴 행이 스냅숏과 달랐다 → 한 행을 쓸 때마다 스냅숏을 갱신하게 바꿨다.
- **관리 화면에서 대표 사진을 바꾸자 품번이 되돌아갔다(11-02).** 관리 화면 이미지 판단에는 품번이 없어서, 빌드가 StockX 조회 결과의 품번으로 채웠다(슈퍼블라스트 2 가 에키덴 품번이 됐다). 처음엔 이전 판단의 품번을 잇게 고쳤다가, 사용자 기준("품번은 대표 이미지를 따른다")에 맞춰 대표 이미지 주소로 캐시에서 상품을 찾게 바꿨다(`01b` 1-3).
- **운영 적재 명령이 권한 판단기에 한 번 막혔다(11-01).** 24번 중 1번, 성공한 명령과 글자 그대로 같은 형태였다 — Claude Code 자동 모드 판단기가 맥락으로 판단해 그때그때 다르다. Secret 에서 비밀번호를 읽어 운영에 쓰는 일이 명령줄에 그대로 드러나는 형태였다. 비밀번호를 스크립트 안으로 넣은 `scripts/load-prod.sh` 와 그 스크립트만 허용하는 규칙으로 바꿨다(11-02, 규칙은 사용자가 넣었다). 첫 실행에서 판단기 없이 통과했다.

#### 4. 남은 한계

- **사람이 돌린다.** 정기 적재 · 정기 가져오기(CronJob)는 없다.
- 관리 화면에서 **새로 넣은 신발**은 카탈로그로 자동으로 옮기지 않는다(구조 변경 — 사람이 후보 목록에 넣는다).
- 스냅숏은 로컬 파일 하나다. 다른 기계에서 적재하면 그 기계의 스냅숏이 없다(`--snapshot` 으로 먼저 적어야 한다).
- `--revert` 는 리뷰 · 찜이 붙은 뒤에는 깔끔하지 않다.
- 카탈로그 밖 시드 1켤레(엔돌핀 스피드 4)는 적재기가 사실 값을 덮지 않아 판단 일부만 따른다.
