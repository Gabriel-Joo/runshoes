# RUNSHOES — 비교 페이지 설계안

상태: **설계안 — 결정 전.** 찜한 신발 가운데 둘을 골라 레이더 차트와 표로 비교한다. 찜이 계정별이 되어(로그인 2단계) 가능해졌다.
비교를 열면 `compare.view` 가 활동 로그에 남는다(3단계에서 API 는 이미 있다) — 나중에 챗봇이 "무엇과 무엇을 비교했는지"를 읽는다.
항목마다 선택지 · 추천 · 이유. 추천만 모으면 맨 아래.

지금 데이터(운영 GET, 2026-10-21, 신발 20켤레):

| 값 | 범위 | 비고 |
|---|---|---|
| weight(g) | 167 ~ 305, 중앙 288 | **167 하나가 튄다**(베이퍼플라이) — 다음 가벼운 것이 201 |
| stackHeight(mm) | 32 ~ 43.5, 중앙 38 | **null 2**(클리프톤 10 · 알파플라이 3) |
| drop(mm) | 5 ~ 10 | 값이 5종뿐 |
| price(원) | 159,000 ~ 339,000, 중앙 209,000 | |

| reviewCount · likeCount | 4~7 · 20~101 | 리뷰 수는 차이가 거의 없다 |
| width · wideAvailable · carbon · stability | 좁음 2 · 보통 14 · 넓음 4 / 와이드 11 / 카본 3 / 안정화 1 | 범주 · 예아니오 |
| midsole | 문자열 | null 1(본디 9) |

## 1. 무엇을 비교하나 — 지금 스키마로 되나

| 선택지 | 내용 |
|---|---|
| **A. 지금 컬럼만** | 스펙(무게 · 스택 · 드롭 · 발볼 · 와이드 · 카본 · 안정성 · 미드솔 · 용도 · 가격)과 반응(평점 · 리뷰 수 · 찜 수) |
| B. 새 컬럼(V4) — 쿠션감 · 반발력 · 접지 같은 "느낌" 점수 | 사람이 매기거나 리뷰에서 뽑아야 한다. 근거 없는 숫자가 차트의 절반을 차지하게 된다 |
| C. 리뷰에서 계산 — 실사용 후기의 누적 거리 · 내구성 | 실사용 후기가 아직 없다(컬럼만 있다) |

**추천 A — V4 가 필요 없다.** 지금 값만으로 차트 축 5개와 표 13줄이 나온다. "느낌" 점수는 근거가 없고, 내구성은 실사용 후기가 쌓인 뒤(C)에 축으로 더한다 — 그때도 리뷰에서 계산하므로 컬럼이 아니라 쿼리다.

## 2. 레이더 축 · 정규화

### 축 — 레이더에는 "클수록 좋다"가 분명한 것만

| 축 | 값 | 방향 | 넣나 |
|---|---|---|---|
| 가벼움 | weight | 작을수록 바깥 | ✓ |
| 쿠션 | stackHeight | 클수록 바깥 | ✓ |
| 가격 부담 적음 | price | 작을수록 바깥 | ✓ |
| 평점 | rating | 클수록 바깥 | ✓ |
| 인기 | likeCount | 클수록 바깥 | ✓ |
| 드롭 | drop | **좋고 나쁨이 없다**(착지 습관에 따라) | 표에만 |
| 리뷰 수 | reviewCount | 4~7 — 차이가 거의 없다 | 표에만(평점 옆) |
| 발볼 · 와이드 · 카본 · 안정성 · 미드솔 · 용도 | 범주 · 예아니오 | 축이 될 수 없다 | 표에만 |

드롭과 스택을 "좋은 쪽"으로 그리면 차트가 거짓말을 한다 — 쿠션(스택)은 "푹신함"으로 읽히니 바깥이 많다는 뜻이 맞지만, 드롭은 아니다. 그래서 축은 다섯.

### 정규화 — 단위가 다른 값을 0~100 으로

| 선택지 | 장점 | 단점(지금 데이터에서) |
|---|---|---|
| min-max(전체 카탈로그) | 단순, 차이의 크기가 보인다 | **무게 167 하나 때문에** 나머지 19켤레가 0.25~1 에 몰려 거의 같아 보인다. 평점 3.7~4.8 은 0.1 차이가 크게 부풀려진다 |
| 고정 기준(예: 무게 150~350g) | 카탈로그가 늘어도 차트가 안 바뀐다 | 기준을 누가 정하나 — 근거가 약하다. 가격 기준은 시간이 지나면 낡는다 |
| **백분위(카탈로그 안의 순위)** | 튀는 값에 강하다. "20켤레 중 상위 15%"처럼 설명할 수 있다 | 차이의 크기(167g vs 201g)는 사라진다 — 그래서 표에 실제 값을 같이 둔다 |

**추천 백분위.** 축마다 카탈로그 안에서 순위를 0~100 으로(동점은 평균 순위, 방향은 축대로). 점 옆 · 툴팁에는 실제 값(`201g · 상위 20%`)을 같이 보인다.
값이 없으면(스택 null) 그 축은 **중심에 점 대신 "정보 없음"** — 0점으로 그리면 "쿠션이 없다"로 읽힌다.

### 어디서 계산하나

| 선택지 | 장점 | 단점 |
|---|---|---|
| 화면에서 — `/api/shoes` 전체를 받아 순위 계산 | 서버 변경 없음 | 신발을 1,000켤레로 늘릴 계획이다 — 둘을 비교하려고 전부 받게 된다(검색을 서버로 옮긴 것과 같은 이유) |
| **서버에서 — `GET /api/compare?ids=2,16`** | 두 켤레와 축별 백분위만 돌려준다. 순위 계산은 카탈로그 전체를 아는 서버가 | API 하나가 는다(json-server 계약 밖 — 기준선에 시나리오를 더한다) |

**추천 서버.** 응답 `{shoes:[…], axes:[{key:"lightness", label:"가벼움", values:[{shoeId, raw, percentile}]}]}`. 누구나 읽을 수 있다(공개 데이터).
조회 기록은 화면이 `POST /api/activity {type:"compare.view"}` 로 — GET 에 쓰기를 붙이지 않는다.

## 3. 어디서 들어오나

| 선택지 | 장점 | 단점 |
|---|---|---|
| 찜 목록 화면 안에서만 | 처음 그린 그림 그대로("찜한 신발을 카드로, 칸 둘에 넣는다") | 찜하지 않은 신발은 비교할 수 없다 |
| 카드마다 "비교에 담기" + 떠 있는 비교 바 | 어디서든 담는다 | 화면마다 상태가 하나 더 — 카드에 버튼이 늘고, 모바일에서 떠 있는 버튼이 또 는다 |
| **`/compare` 한 곳 — 위에 칸 둘, 아래 찜 카드** | 들어오는 길이 하나라 단순하다. 링크로 공유할 수 있다 | 찜하지 않은 신발은 모달의 "비교하기"로(아래) |

**추천 `/compare`.** 들어오는 길:
- 헤더 "비교"(로그인했을 때) — 찜 카드에서 둘을 고른다
- 상세 모달의 "비교하기" — 그 신발을 첫 칸에 넣고 `/compare?ids=<id>` 로. 찜하지 않은 신발도 이 길로 비교할 수 있다
- 홈 "찜한 것만 보기"가 켜져 있을 때 정렬 줄 옆 작은 링크 "찜한 것 비교하기"

찜이 없으면: "찜한 신발이 없어요 — 홈에서 하트를 눌러 보세요"와 홈 링크. 로그인 안 했으면 아래 5절.

## 4. 둘만? 셋도?

| 선택지 | 장점 | 단점 |
|---|---|---|
| **둘** | 레이더 두 겹은 분명히 읽힌다. 표가 360px 에서도 두 칸 | 셋을 보고 싶은 사람이 있다 |
| 셋까지 | 후보 셋을 한 번에 | 레이더 세 겹은 겹치는 곳이 많아 읽기 어렵다. 360px 에서 표 세 칸이 좁다(한 칸 약 100px) |
| 제한 없음 | — | 레이더가 무의미해진다 |

**추천 둘.** 다만 API(`?ids=` · `compare.view` 의 2~3개)와 URL 은 셋까지 받게 열어 둔다 — 화면만 둘로 시작하고, 써 보고 셋을 열지 정한다.

## 5. 비교 상태를 URL 에

| 선택지 | 장점 | 단점 |
|---|---|---|
| 화면 상태만 | 단순 | 새로고침 · 뒤로 가기에 사라진다. 공유할 수 없다 |
| **`/compare?ids=2,16`** | 새로고침 · 뒤로 가기 · 공유가 된다. 모달의 "비교하기"가 같은 길을 쓴다 | 링크를 받은 사람은 그 두 켤레를 보지만 자기 찜 목록은 다르다 |
| 저장(서버에 비교 목록) | 기기를 바꿔도 | 테이블 · API 가 는다. 지금 필요한 사람이 없다 |

**추천 URL.** 칸을 바꿀 때마다 `replace` 로 고친다(뒤로 가기가 칸 바꿈마다 쌓이지 않게).
**링크로 들어온 사람은 로그인 없이도 비교 결과를 본다**(공개 데이터) — 칸을 바꾸려면(찜 목록에서 고르려면) 로그인. 없는 id · 숫자가 아닌 것은 버리고 남은 것만 칸에 둔다.

## 6. 차트 라이브러리

지금 의존성에 차트가 없다(React · react-router 만). 번들은 gzip 약 86KB.

| 선택지 | 크기(gzip, 어림) | 장점 | 단점 |
|---|---|---|---|
| Recharts | 약 90KB+ | React 다운 API, 레이더 있음 | 번들이 두 배 가까이. 레이더 한 장에 쓰기엔 크다. 토큰 색 · 글자 크기를 props 로 따로 넘겨야 한다 |
| Chart.js + react-chartjs-2 | 약 70KB | 많이 쓰인다, 애니메이션 | canvas — 글자가 CSS 토큰을 못 받고, 화면 읽기 · 확대 · 인쇄가 SVG 보다 불리 |
| Nivo radar | 큼(d3 포함) | 예쁘다 | 가장 무겁다 |
| **직접 SVG(컴포넌트 하나)** | 0 | 축 다섯 · 다각형 둘 · 눈금은 삼각함수 몇 줄. CSS 토큰 · 반응형 · `aria` 를 그대로 쓴다. "정보 없음" 같은 규칙을 마음대로 | 툴팁 · 애니메이션을 직접. 다른 종류 차트가 필요해지면 다시 정한다 |

**추천 직접 SVG.** 레이더 한 장(축 5, 시리즈 2)이라 라이브러리가 주는 것보다 맞추는 비용이 크다. 접근성: 차트는 `role="img"` + 축별 값 요약을 `aria-label` 에, 같은 내용이 표에도 있다.

## 7. 모바일

| 선택지 | 장점 | 단점 |
|---|---|---|
| **레이더를 그대로, 크기만 맞춘다** | 화면의 정체성이 그대로. 축 다섯이면 320px 정사각형에서도 읽힌다 | 축 이름이 길면 넘친다 |
| 모바일은 축별 맞대기 막대(나비 차트)로 | 좁은 폭에서 가장 읽기 쉽다 | 데스크톱과 모양이 달라 "같은 화면"이 아니다. 차트를 두 벌 만든다 |
| 차트를 숨기고 표만 | 단순 | 비교 페이지의 핵심을 빼는 것 |

**추천 레이더 그대로 + 표.** 차트는 폭 100%의 정사각형(최대 480px), 축 이름은 짧게(가벼움 · 쿠션 · 가격 · 평점 · 인기), 767px 이하에서는 눈금 숫자를 숨기고 범례를 차트 위 칩 두 개로.
표는 차트 아래에 — 첫 열은 항목 이름, 두 열은 신발(헤더에 모델명 · 이미지, 스크롤해도 머리가 붙는다). 표에는 **더 나은 쪽을 굵게** — 가볍다 · 싸다 · 평점이 높다처럼 방향이 분명한 줄만. 드롭 · 스택 · 범주는 표시하지 않는다(차이일 뿐).
여섯 폭(1440 · 1280 · 1024 · 768 · 390 · 360)에서 넘침 · 겹침을 잰다.

## 8. 시험 · 계약 · 배포

- 단위: 백분위(동점 · 방향 · null), URL 의 ids 다듬기
- 계약: `GET /api/compare` 시나리오(두 켤레 · 셋 · 없는 id · 하나뿐 · 같은 id 둘) — 기준선 spring-v3 에 더한다(쓰기 없음, 운영 읽기 전용 확인에도 든다)
- 화면: 칸 고르기 · 바꾸기 · URL · 링크로 들어오기(비로그인) · 찜 없음 · 정보 없음 축 · 여섯 폭
- 배포: 마이그레이션 없음 — 이미지 Sync 하나
