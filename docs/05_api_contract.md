#### 2. 왜 이렇게 했나

- **화면을 고치지 않고 백엔드를 바꾸는 것이 목표였다(2026-10-18~21).** 과제 요건은 json-server 였고, 같은 API 계약을 Spring Boot + MySQL 로 구현했다. 문서나 계획서가 아니라 **실제 응답을 녹화해 정답으로** 삼았다 — 계획서(코드를 읽고 쓴 것)가 실제와 다른 곳이 넷 나왔다(3절). [c:a6bf21e]
- **이상해 보이는 모양도 계약이다.** DELETE 의 `{}`, OPTIONS 204, 정렬 동점의 id 순은 프런트가 기대는 동작이라 그대로 뒀다. 프런트가 쓰지 않는 json-server 동작(모르는 필드 저장 등)은 안전한 쪽으로 바꿨다(1-6). [code:backend/src/main/java/com/kopo17/runshoes/api/JsonServerController.java:87] [code:backend/src/main/java/com/kopo17/runshoes/config/ApiHeadersFilter.java:20] [code:backend/src/main/java/com/kopo17/runshoes/api/ListQuery.java:91]
- **키를 더하기만 한다.** 화면 · 적재기 · 계약 시험이 옛 키에 기대고 있다. 키를 바꾸거나 빼면 셋이 함께 깨진다. 그래서 와이드 넷도 `wideAvailable` 을 두고 `wideScope` 를 더했다(V12). [code:backend/src/main/java/com/kopo17/runshoes/api/ShoeCollection.java:297-298] [code:backend/src/main/java/com/kopo17/runshoes/api/ShoeCollection.java:309]
- **기준선을 다시 녹화하지 않는다(2026-10-24).** 다시 녹화하면 무엇이 바뀌었는지 추적이 사라진다. 옛 기준선 + 허용 키 + "의도한 차이 목록"이 변경 이력이 된다. [code:contract/run-spring-local.sh:160] [code:contract/README.md:92]
- **서버가 정하는 값은 본문을 믿지 않는다(V3).** 평점 · 찜 수 · 작성자 · 시각을 본문에서 받으면 누구나 바꿀 수 있다. admin 이 보내도 버린다. [code:backend/src/main/java/com/kopo17/runshoes/api/ShoeCollection.java:32] [code:backend/src/main/java/com/kopo17/runshoes/api/ReviewCollection.java:24]
