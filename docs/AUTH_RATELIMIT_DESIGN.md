# RUNSHOES — 로그인 3단계 설계안: 시도 제한(429)과 활동 로그

상태: **추천 묶음대로 구현 — 로컬 검증까지, 배포 전**(2026-10-21). 로그인 1 · 2단계는 운영 중이다([AUTH_DESIGN.md](AUTH_DESIGN.md)).
코드: `backend/…/auth/RateLimiter` · `EmailKey`, `backend/…/activity/`(ActivityLogger · ActivityController · ActivityCleanup), 설정 `application.yml` 의 `app.ratelimit` · `app.activity`.
둘 다 V3 가 만든 `activity_logs` 를 쓴다 — 시도 제한은 그 행을 **세고**, 활동 로그는 그 행을 **남긴다**. 테이블은 있고 아직 아무것도 쓰지 않는다.
항목마다 선택지 · 추천 · 이유. 추천만 모으면 맨 아래 "추천 묶음".

```
activity_logs: id · occurred_at(UTC ms) · user_id(FK, SET NULL) · event · target_type · target_id · meta(JSON) · ip · user_agent · request_id
인덱스: (user_id, occurred_at) · (event, occurred_at) · (ip, occurred_at)
```

확인한 사실(2026-10-21): ingress-nginx 는 `X-Forwarded-For` 를 `$remote_addr`(= cloudflared Pod)로 덮어쓰고 `X-Request-ID` 를 넘긴다 —
방문자 IP 는 `CF-Connecting-IP` 에만 있다(`auth/RequestInfo` 가 이미 그 순서로 읽는다).

## 1. 무엇을 몇 번까지, 얼마나 막나 — 기준은 IP? 계정?

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. IP 만 | 단순. 한 곳에서 여러 계정을 두드리는 것을 막는다 | 같은 학교 · 회사 NAT 뒤 사람들이 같이 막힌다. IP 를 바꿔 가며 한 계정을 노리면 못 막는다 |
| B. 계정(이메일)만 | 한 계정을 겨냥한 추측을 정확히 막는다 | 한 IP 에서 계정 100개를 하나씩 두드리는 것(spraying)은 못 막는다. 남의 계정을 일부러 잠글 수 있다 |
| **C. 둘 다, 기준을 다르게** | 각자의 빈틈을 서로 메운다 | 규칙이 둘 — 문서 · 시험이 늘어난다 |

**추천 C.**

| 대상 | 무엇을 센다 | 허용 | 막는 시간 |
|---|---|---|---|
| 로그인 — 계정 | 그 이메일의 `auth.login.failure` | 15분에 **5번** | 마지막 실패에서 15분 |
| 로그인 — IP | 그 IP 의 `auth.login.failure` | 15분에 **20번** | 15분 |
| 비밀번호 변경의 "지금 비밀번호" 틀림 | 로그인 실패와 같이 센다(그 계정) | 위와 같음 | 위와 같음 |
| 가입 | 그 IP 의 `auth.signup`(성공) | 1시간에 **10건** | 1시간 |
| 닉네임 미리 확인 | 세지 않는다 | — | — |
| refresh | 세지 않는다 — 쿠키 없이는 아무것도 못 하고, 재사용 감지가 따로 있다 | — | — |

- **창은 슬라이딩**(지금부터 15분 전까지의 행을 센다). 로그인에 **성공하면 그 계정의 실패는 리셋**(성공 행보다 뒤의 실패만 센다) — 오타 몇 번 뒤 들어간 사람이 다음에 바로 잠기지 않게
- IP 기준을 계정보다 넉넉히(20) 둔 이유: 같은 공인 IP 뒤에 여러 사람이 있을 수 있다(학교 · 카페). 계정 5번은 사람이 실수로 넘기기 어렵고, 기계가 추측하기에는 턱없이 적다
- **없는 이메일도 똑같이 센다** — 존재하는 계정만 잠기면 "6번째에 429 가 나오면 가입된 이메일"이라는 단서가 된다(2절)
- 비밀번호를 검사하기 **전에** 센다 — 잠겨 있으면 BCrypt 를 돌리지 않는다(추측 · 부하 둘 다)

## 2. 잠긴 동안 맞는 비밀번호가 오면?

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 막는다(똑같은 429)** | 잠긴 동안에는 추측이 맞았는지 알 수 없다 — 잠금이 의미를 갖는다 | 공격자가 남의 계정을 15분씩 잠글 수 있다(계정 DoS) |
| B. 맞으면 통과 | 진짜 주인은 잠겨도 들어온다 | 공격자도 "통과 = 정답"으로 계속 추측한다 — 잠금이 추측을 막지 못하고 늦추지도 못한다 |
| C. 그 IP 만 막는다(계정 + IP 짝) | 다른 곳의 진짜 주인은 들어온다 | IP 를 바꾸면 다시 5번 — 계정 기준의 뜻이 약해진다 |

**추천 A.** 잠금은 맞는 비밀번호에도 같은 응답이어야 의미가 있다. 남이 잠그는 위험은 짧은 시간(15분) · IP 기준(한 IP 가 여러 계정을 잠그려면 20번에서 막힌다)으로 줄인다.
포트폴리오 사이트의 규모에서는 이 정도면 된다. admin 이 잠금을 푸는 화면은 두지 않는다(시간이 지나면 풀린다).

## 3. 기록할 이벤트 · 보관 기간 · 정리

### 이벤트

| 분류 | 이벤트 | 남기는 때 | target |
|---|---|---|---|
| 인증 | `auth.signup` · `auth.login.success` · `auth.login.failure` · `auth.login.blocked`(429) · `auth.refresh.reuse` · `auth.logout` · `auth.password.change` · `auth.password.failure` · `user.nickname.change` | 인증 API 안 | user 또는 email(아래) |
| 쓰기 | `review.create` · `review.update` · `review.delete` · `like.add` · `like.remove` · `review_like.add` · `review_like.remove` | 쓰기 API 안(실제로 바뀐 때만 — 멱등 PUT 이 그대로면 남기지 않는다) | review · shoe |
| 조회 | `shoe.view`(모달을 열 때, 같은 사람 · 같은 신발 30분에 한 번) · `compare.view`(비교 화면, `{shoeIds}`) | `POST /api/activity` — 로그인한 사람만 | shoe |

- **refresh 성공은 남기지 않는다** — 쓰는 사람마다 15분에 한 줄씩 쌓이는데 읽을 곳이 없다. 재사용 감지(`auth.refresh.reuse`)만
- 비로그인 조회는 남기지 않는다 — 챗봇은 로그인한 사람의 맥락만 읽는다. 익명 집계가 필요해지면 Loki 쪽(HTTP 로그)
- **카운팅 키(인증 이벤트만)**: 로그인 성공 · 실패 · 429 · 비밀번호 확인 실패에는 `target_type='email'`, `target_id` = 정규화한 이메일의 HMAC-SHA256 앞 8바이트(BIGINT)를 넣는다.
  **시도 제한이 세는 데만 쓴다** — 없는 이메일도 같은 기준으로 세야 하는데, 없는 이메일에는 user_id 가 없기 때문이다. 사람은 이 값을 읽지 못하고 읽을 필요도 없다
- **사람이 읽는 것은 user_id 다**: 활동 로그를 나중에 보는 사람 · 챗봇은 `user_id` 로 `users` 를 조인해 누구인지 안다(계정이 있는 실패에도 user_id 를 같이 넣는다).
  그래서 활동 로그에는 이메일이 필요 없다 — 원문을 남기지 않는 이유는 HMAC 이 아니라 **user_id 로 충분하기 때문**이다(4절)

### 같은 트랜잭션인가

| 이벤트 | 어떻게 | 이유 |
|---|---|---|
| 쓰기 · 조회 · 인증 성공 | 그 작업과 **같은 트랜잭션** | 롤백된 일의 로그가 남지 않는다 |
| 로그인 실패 · 429 · 재사용 감지 | **따로 커밋**(`REQUIRES_NEW`) | 이 요청은 401 · 429 로 끝난다 — 같은 트랜잭션이면 실패 기록이 같이 사라져 **시도 제한이 세지 못한다** |

### 보관 · 정리

| 선택지 | 장점 | 단점 |
|---|---|---|
| 영구 | 단순 | 계속 자란다. 쓰지 않는 IP · UA 를 계속 들고 있다 |
| 하나로(예: 90일) | 규칙 하나 | 챗봇이 "예전에 본 신발"을 못 읽는다 |
| **분류별** | 쓰임에 맞춘다 | 규칙 둘 |

**추천 분류별**: 인증 **90일**(시도 제한은 1시간이면 되지만, 이상한 로그인을 나중에 보려면 몇 달) · 쓰기 · 조회 **180일**(챗봇의 "최근 본 · 쓴 것"). 지운 계정의 행은 user_id 가 NULL 이 된다(FK SET NULL).

정리 방법:

| 선택지 | 장점 | 단점 |
|---|---|---|
| **앱 안 `@Scheduled`(매일 04:00 KST)** | 코드와 같이 git · 시험에 들어 있다. 이미지 하나 | 앱이 내려가 있으면 그날은 건너뛴다(다음 날 한다 — 문제없다) |
| K8s CronJob | 앱과 독립 | 이미지 · 매니페스트 · DB 계정이 하나 더 |
| MySQL EVENT | 앱 밖에서 돈다 | 규칙이 DB 안에 숨어 git 에 없다 |

**추천 `@Scheduled`.** `DELETE … WHERE event IN (…) AND occurred_at < ? LIMIT 5000` 을 0건이 될 때까지 — `(event, occurred_at)` 인덱스를 타고, 한 번에 오래 잠그지 않는다.
Pod 가 여럿이 되어도 같은 DELETE 를 두 번 할 뿐이다(멱등). 지운 수는 앱 로그에 한 줄.

## 4. IP · User-Agent 를 남기는 범위

| 선택지 | 장점 | 단점 |
|---|---|---|
| 모든 이벤트에 전체 IP · UA | 나중에 무엇이든 본다 | 쓰지 않는 개인 정보를 많이 쌓는다 |
| 잘라서(IPv4 /24 · IPv6 /48) | 덜 개인적 | IP 기준 시도 제한을 할 수 없다(같은 대역 전체가 묶인다) |
| 해시 | 같은 IP 인지는 안다 | 이상한 로그인을 사람이 볼 때 쓸모가 없다 |
| **인증에만 전체, 나머지는 없음** | 필요한 곳에만 | 규칙 하나 더 |

**추천: 인증 이벤트에만 IP(전체) · UA(255자로 자름)**, 쓰기 · 조회에는 남기지 않는다(NULL).
IP 기준 시도 제한에는 원래 IP 가 있어야 하고, 이상한 로그인을 볼 때도 있어야 한다 — 90일 뒤 지운다. 쓰기 · 조회의 IP 는 아무도 읽지 않는다.
이메일 원문은 어디에도 남기지 않는다 — 이유가 둘이다. 계정이 있는 이벤트는 **user_id 로 충분하다**(사람이 읽을 때 조인한다).
계정이 없는 로그인 실패는 오타 낸 남의 이메일일 수 있어 남길 까닭이 없다 — 이때는 시도 제한이 세도록 **카운팅 전용 HMAC 키**만 둔다(3절). HMAC 은 읽기용이 아니다. IP 는 `CF-Connecting-IP` 를 믿는다 — 클러스터 안에서 VIP 로 바로 붙으면 꾸밀 수 있지만, 그 길은 밖에 열려 있지 않다.

## 5. 429 응답과 화면

```
HTTP/1.1 429
Retry-After: 540
{"error":{"code":"RATE_LIMITED","message":"로그인 시도가 너무 많아요. 9분 뒤에 다시 해 주세요.","retryAfter":540}}
```

- 인증 API 의 다른 오류와 같은 모양(`{error:{code, field?, message}}`) — 화면은 message 를 그대로 보여 준다. 분은 올림. 계정 · IP 어느 쪽에 걸렸는지 말하지 않는다
- **맞는 비밀번호 · 없는 이메일이어도 같은 응답**(1 · 2절)
- 가입: "가입 시도가 너무 많아요. N분 뒤에 다시 해 주세요." 비밀번호 변경: 로그인과 같은 문구

| 선택지(화면) | 추천 |
|---|---|
| 문구만, 버튼은 그대로(눌러도 서버가 다시 429) | |
| **문구 + 남은 시간 동안 버튼을 끄고 분 단위로 줄여 보인다**(`Retry-After` 를 쓴다) | ✓ — 눌러 봐야 소용없다는 것을 화면이 먼저 알려 준다. 새로고침하면 서버가 다시 알려 준다(브라우저에 저장하지 않는다) |

## 6. activity_logs 가 커질 때

어림(포트폴리오 규모, 하루 방문 수십~수백): 조회가 가장 많다 — 사람당 하루 신발 10개를 열면 하루 수백~수천 행, 180일이면 수십만 행. 행 하나 수백 바이트 → 수십~수백 MB. PVC 2Gi 안이다.

| 대책 | 언제 | 메모 |
|---|---|---|
| **보관 기간 + 매일 정리**(3절) | 처음부터 | 크기의 상한을 정한다 — 이것이 본 대책 |
| 조회 30분 중복 제거 | 처음부터 | `shoe.view` 를 줄인다 |
| 크기 보기 | 처음부터 | 정리 job 이 남은 행 수를 로그에 남긴다. 100만 행을 넘으면 다시 본다 — 알아차리는 길은 아래 |
| 월 단위 파티션 | 크게 늘면 | MySQL 은 **FK 가 있는 테이블을 파티션할 수 없다** — user_id FK 를 풀어야 한다. 그만큼 커질 일이 없으면 하지 않는다 |
| 오래된 것을 Loki · 파일로 내보내기 | 크게 늘면 | 챗봇이 읽을 필요가 없는 것만 |

**알아차리는 길** — 지켜보는 사람이 없어도 걸리게, 사람이 반드시 보는 곳에 둔다:
- 정리 job 이 매일 남은 행 수를 쓰고, **50만 행을 넘으면 WARN**(`activity_logs 가 커졌다 — N행`). Loki 를 붙이면 이 한 줄에 경보를 건다
- **배포 뒤 확인 스크립트(`post-sync-*.sh`)가 행 수와 하루 증가량을 출력**하고 50만이 넘으면 눈에 띄게 표시한다 — 배포는 자주 하고, 그때마다 사람이 결과를 읽는다.
  지금은 모니터링이 없어서 이것이 실제로 사람이 보는 지점이다. 100만에 닿기 전(50만)에 걸리게 문턱을 낮춰 둔다

## 7. 새 마이그레이션(V4)이 필요한가

**필요 없다.** V3 의 테이블 · 인덱스로 된다.

| 쓰임 | 쿼리 | 타는 인덱스 |
|---|---|---|
| 계정 — 로그인 실패 수 | `event='auth.login.failure' AND target_type=? AND target_id=? AND occurred_at > ?` | `(event, occurred_at)` — 15분 동안의 실패 행만 훑는다 |
| 계정 — 마지막 성공 | `event='auth.login.success' AND user_id=? ORDER BY occurred_at DESC LIMIT 1` | `(user_id, occurred_at)` |
| IP — 실패 수 · 가입 수 | `ip=? AND event=? AND occurred_at > ?` | `(ip, occurred_at)` |
| 정리 | `event IN (…) AND occurred_at < ?` | `(event, occurred_at)` |
| 챗봇 — 내 최근 활동 | `user_id=? ORDER BY occurred_at DESC` | `(user_id, occurred_at)` |

- 이메일을 키로 세는 칸은 `target_type='email'` + `target_id`(HMAC 앞 8바이트)로 — 새 컬럼 없이. 64비트라 겹칠 일은 시도 제한에서 무시해도 된다
- 실패 행이 아주 많아지면 `(event, target_type, target_id, occurred_at)` 인덱스를 더할 수 있다 — 그때의 마이그레이션이다. 지금은 아니다
- 이미 정한 V4(`reviews.user_id` NOT NULL, 공용 `liked` 칸 삭제)는 이와 따로 간다

## 8. 시험 · 계약

- 단위: 창 계산(슬라이딩 · 성공 리셋), HMAC 키, 메시지의 분 올림
- 로컬 API: 계정 5번 → 6번째 429(맞는 비밀번호도) · 없는 이메일도 같음 · IP 20번 · 가입 10건 · `Retry-After` · 15분 뒤 풀림(시계를 당겨서 — 테스트 설정으로 창을 줄인다) · 실패 기록이 401 뒤에도 남는다
- 화면: 429 문구 · 버튼 끄기 · 남은 분이 줄어든다
- 계약: `AUTH_SCENARIOS` 에 429 시나리오(계약 계정으로 6번), 쓰기 시나리오의 activity_logs 행 수 — 기준선 `spring-v3` 를 다시 녹화한다(의도한 변경)
- 배포: 마이그레이션이 없어 이미지 Sync 하나. 배포 뒤 처음 15분은 셀 기록이 없다(그 전의 실패는 세지 않는다)

## 구현하며 정한 것

- **막힌 시도(`auth.login.blocked`)는 실패로 세지 않는다** — 잠긴 뒤 두드릴수록 잠금이 길어지지 않게. 그래서 "마지막 실패에서 15분"이 그대로 지켜진다
- 가입은 "그 IP 의 최근 10건 가운데 가장 오래된 것에서 1시간 뒤" 풀린다 — 문구의 분도 그 기준(60분이 아닐 수 있다)
- `compare.view` 는 target 없이 meta `{shoeIds}`(정렬해 둔다) — 같은 조합 30분 중복 제거는 JSON 비교
- 실패 기록은 `REQUIRES_NEW` 로 따로 커밋 — 같은 트랜잭션이면 401 과 함께 사라져 셀 수 없다(로컬 시험으로 확인: 401 뒤에도 행이 남는다)
- activity_logs 를 읽는 API 는 아직 없다 — 사람은 DB 에서, 챗봇은 그 단계에서
- 시험할 때: 정리 시각은 `ACTIVITY_CLEANUP_CRON`, 경고선은 `APP_ACTIVITY_WARN_ROWS` 로 줄여 본다. IP 기준은 `CF-Connecting-IP` 를 바꿔 가며
