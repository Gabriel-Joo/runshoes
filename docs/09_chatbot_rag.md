#### 1. 검색 — 벡터 DB 쓰지 않는다

**결정:** 메모리 색인 + BM25 하이브리드. Milvus 쓰지 않는다.

근거

- 문서 약 3,660건(리뷰 1,800 + 설명문 약 1,860 — 310켤레를 문장 단위로 쪼갠 수, 11절). 1024차원 벡터로 약 15MB. 전수 비교해도 1ms 안쪽이다.
- 런슈즈 데이터는 계속 바뀐다(방문자 리뷰, 관리자 스펙 수정). Milvus 면 upsert · 삭제 동기화를 상시 관리해야 한다. 메모리 색인은 주기적으로 API 를 읽어 바뀐 것만 재임베딩하면 끝이다.
- 호스트 Milvus 는 펫퍼민트가 쓰는 임시 docker standalone 이다(`milvus-standalone`, `milvusdb/milvus:v3.0.2` — 컬렉션은 `petmint_*` 8개와 `hr_regulation`). 거기 의존하면 펫퍼민트 작업에 런슈즈가 묶인다.

단점과 대응

| 단점 | 대응 |
|---|---|
| Pod 시작 시 전량 임베딩 | 결과를 파일 캐시. 해시로 바뀐 것만 재계산 |
| 검색 로직 직접 구현 | 이 규모에선 각 수십 줄 |
| Pod 여러 개면 중복 보유 | 15MB 라 문제 아님 |

교체 가능하게 둔다

`SearchIndex` 인터페이스로 추상화하고 `MemoryIndex` 를 구현한다. 챗봇 코드는 인터페이스만 부른다. 아래 중 하나라도 넘으면 벡터 DB 로 바꾼다.

- 문서 1만 건 초과 — 약 3,660건 기준으로도 그대로 둔다. 1만 건은 리뷰가 두 배 넘게 늘어야 닿는 수치이고, 그 지점이면 리뷰 전량 주입(6절) 등도 같이 다시 볼 시점이다(2026-11-10 사용자)
- Pod 시작 임베딩 30초 초과
- Pod 2개 이상 운영

BM25 를 같이 쓰는 이유

리뷰 중앙값이 44자다. 짧은 글에서 임베딩은 뭉뚱그려진다. "발볼" · "뒤꿈치" 같은 낱말 일치와 PEBA · EVA · TPU 같은 고유명사는 BM25 가 정확하다. 한국어 토큰은 글자 2-gram 으로 시작하고 평가로 확인한다.

#### 2. 임베딩 · 리랭커 — model-service 로 분리 (변경)

cc안은 bge-m3 를 Ollama 에 올리는 것이었으나, **KURE-v1 을 쓰되 펫퍼민트 서비스에 끼워 넣지 않는다. KURE-v1 과 bge-reranker-v2-m3 를 함께 두 프로젝트 공용 서비스로 분리한다.**

model-service (호스트 프로세스, 모델은 지금 그대로 — KURE-v1 fp32 · bge-reranker-v2-m3 fp16 1024토큰)

- `POST /embed` — 텍스트[] → 벡터[]
- `POST /rerank` — 질의 + 문서[] → 점수[](넣은 순서대로)
- `GET /health`

- 펫퍼민트: `search_service` 에서 모델 로딩을 빼고 이 서비스 호출로 바꾼다. 검색 로직(하이브리드 · 필터 · 정렬)은 그대로 펫퍼민트에 남는다.
- 런슈즈: 챗봇이 이 서비스를 부른다(5단계).

이름 — 처음엔 `embedding-service` 였다. 리랭커도 함께 빼고, 나중에 다른 모델이 들어와도 이름을 다시 바꾸지 않도록 `model-service` 로 정했다(2026-11-11 사용자).

근거

- 두 모델은 지금 펫퍼민트 `search_service`(systemd `petmint-search`, `192.168.122.1:8100`) 프로세스 안에 올라가 있다. 모델 파일은 공유돼도 GPU 메모리는 프로세스마다 따로 잡힌다 — 런슈즈가 같은 모델을 자기 프로세스에 올리면 그만큼 또 쓴다.
  - 그 프로세스가 지금 5.0GB 를 잡고 있다(2026-11-11 `nvidia-smi`, Ollama 에 올라간 모델이 없을 때). 무게로 보면 KURE fp32 약 2.2GB + 리랭커 fp16 약 1.1GB, 나머지는 CUDA 문맥과 PyTorch 가 붙들어 둔 추론용 캐시다.
  - Ollama 가 `gemma4:e4b`(9.6GB)를 올리면 합계 약 15GB / 16GB 다(2026-11-10 측정 때 13GB — 그때 펫퍼민트는 3.5GB 였고 캐시가 늘었다).
- 그렇다고 펫퍼민트 서비스에 런슈즈 엔드포인트를 넣으면 두 프로젝트가 한 프로세스에 묶인다.
- 임베딩과 리랭커는 둘 다 텍스트를 넣으면 숫자가 나오는 순수 함수다. 코퍼스 · 프로젝트와 무관하다 — 그래서 둘을 함께 뺀다. 한 프로세스에 그대로 옮기므로 GPU 사용량은 지금과 같다.

어디 · 어떻게(2026-11-11 사용자 확정)

- 코드 · 문서 · 런북: `~/AI_programming/model-service/` 독립 저장소(README · `docs/runbook-cutover.md`). 두 프로젝트 어느 쪽 것도 아니라 밖에 둔다.
- 주소: `192.168.122.1:8200` — systemd 유닛 `model-service`. venv 는 펫퍼민트와 같은 `~/llm_env`(판이 같아야 결과가 비트까지 같다).
- 펫퍼민트 search-service 는 `PETMINT_MODEL_URL` 이 있으면 model-service 를 부르고, 없으면 예전처럼 자기 프로세스에 올린다(노트북 · 되돌리기 경로).
- 런슈즈 Pod 에서는 Ollama(`:11434`)와 같은 길(`192.168.122.1`)이다.
- 전환: petmint-search 재시작 한 번(약 6초 끊김). 전후 대조는 펫퍼민트 검색 회귀 세트 103 + 26문항의 `/search` 원시 응답과 `/embed` 벡터를 비트까지 — 운영 전환 뒤 391건 다름 0(2026-11-11). 상태는 13절.

새로 생긴 약점 둘

- **단일 장애점이 넓어졌다.** model-service 가 죽으면 펫퍼민트와 런슈즈 **둘 다** 검색이 멈춘다. 전에는 펫퍼민트만 멈췄다. 런슈즈 쪽에서는 의존이 하나 늘었다 — 챗봇의 경험 · 후기 갈래(0절)가 model-service 에 기댄다. 용어 · 스펙 · 비교 · 추천 갈래는 임베딩을 쓰지 않으므로 영향이 없다(5단계에서 그렇게 나눈다).
- **재부팅 순서가 한 단계 늘었고, 시험하지 않았다.** `network → docker · libvirtd → model-service → Milvus 대기 → petmint-search`. 다음 재부팅 때 확인한다(model-service 런북 8절).

런슈즈 챗봇은 리랭커를 1차에 쓰지 않는다. 검색 품질이 모자랄 때 평가 결과를 보고 켠다 — model-service 에 이미 있으니 켤 때 GPU 를 더 쓰지 않는다.

#### 3. 비교 · 추천 — Spring API 로 이관 (변경)

cc안의 A(챗봇을 Node 로 다시 쓰기)는 쓰지 않는다. 프런트 React / 백엔드 Spring 방향이 정해져 있다.

옮기기 전 — 둘 다 브라우저에서 돌았다(2026-11-10 작업 3 에서 옮김, 13절).

- 비교 → `src/utils/compare.ts` (순수 함수로 분리돼 있었다) → 서버 `compare/ComparePolicy`
- 추천 → `src/pages/Recommend.tsx` 206~350줄 (컴포넌트 안의 `evaluate`) → 서버 `compare/RecommendPolicy`

목표

- `GET /api/compare` — 신발 id 들(`?ids=`) 또는 고른 신발 하나(`?pick=`, 자동 채우기까지) → 등수 · 밴드 · 무게 환산 여부(13절 — GET 인 까닭)
- `GET /api/recommend` — 조건 5칸 → 상위 3 + score + reasons

프런트는 계산하지 않고 API 를 불러 그리기만 한다. 챗봇도 같은 API 를 부른다.

근거

- 비교 · 추천은 도메인 로직이다. 화면이 아니라 백엔드가 판단할 일이다.
- json-server 시절 백엔드에 로직 둘 곳이 없어 프런트에 쓴 것이고, Spring 전환 때 옮기지 않은 상태다.
- 파이썬에 다시 구현하면 로직이 두 벌 된다. 가중치 하나 고치면 양쪽을 고쳐야 하고, 둘이 다른 답을 내면 버그다.

추천 입력 5칸 (현행 그대로): `purpose` / `width` / `stability` / `cushion` / `price`

이관 시 지킬 것

- 점수 가중치와 동점 처리(평점 × 리뷰 수 보정 + 찜)를 그대로 옮긴다.
- 화면 동작이 바뀌면 안 된다. 이관 전후 결과가 같은지 확인한다.

#### 4. 무게 환산

**결정:** 환산 컬럼을 만들고 화면 · 챗봇이 함께 쓴다.

> 구현(2026-11-10, 작업 2 — 운영 적용: V15 · V16 · 이미지 `40586d6eb722`, 환산값 281 · 기준 모름 29): V15 `shoes.weight_norm_270`(DB 생성 컬럼 VIRTUAL, API `weightNorm270`) · 비교하기 등수 · 그래프 · 비슷한 신발 거리. 규칙 · 계수 · 출처는 `01a_catalog_sources.md` 1-3a 로 옮겼고(아래 "docs 에 환산 규칙 절"), 화면 표시는 `08_compare.md` 1-7. 설계에서 달라진 것은 아래 "구현에서 정한 것".

현황 (`official_weight_size`, 공개 API `weightSize` 로 셈)

| 기준 | 켤레 |
|---|---|
| M9 | 211 |
| M10 | 37 |
| M9.5 | 16 |
| M10.5 | 9 |
| M8.5 | 8 |

전에는 비교하기가 M9 만 등수 · 그래프에 넣어 310개 중 99개가 무게 비교에서 빠졌다. 지금은 기준 모름 29개만 빠진다(281켤레).

환산 계수: **반 사이즈당 2.6%**

- 근거: RunRepeat 실측 — 반 사이즈당 중앙값 2.6%, 모델별 1.66~3.60%, 300g 기준 반 사이즈당 5~10.8g.
- 측정 범위: US 8~12.5, 러닝화 4종 실측.
- 출처: https://runrepeat.com/guides/how-much-does-the-weight-vary-across-different-running-shoe-sizes (웹 클로드가 검색으로 확인, 2026-11-10 사용자)

| 기준 | 270mm(M9) 환산 |
|---|---|
| M8.5 | × 1.026 |
| M9 | 그대로 |
| M9.5 | ÷ 1.026 |
| M10 | ÷ 1.026² (약 −5.0%) |
| M10.5 | ÷ 1.026³ (약 −7.4%) |

규칙

- 공시값에서만 환산한다. 실측값(19켤레)은 건드리지 않는다.
- 기준이 비어 있는 29켤레는 환산하지 않는다. "기준 모름"을 유지한다.
- 답변 · 화면에 원값을 먼저 쓰고 환산값은 괄호에. "약"을 붙인다.
- 환산 후 차이가 8g 미만이면 우열을 판단하지 않는다. 모델별 편차(1.66~3.60%)에서 나올 수 있는 오차 범위이기 때문이다.
- docs 에 "환산 규칙" 절을 새로 두고 계수 · 출처를 기록한다.

표시 예 — 규칙의 양쪽을 보인다

예 1 — 판단하는 경우

> B는 285g(280mm 기준)이에요. 270mm로 환산하면 약 271g이라, 258g인 A보다 무거운 편이에요.

(285 ÷ 1.026² = 270.7, 차이 12.7g → 8g 이상이라 우열을 말한다)

예 2 — 판단하지 않는 경우

> A는 265g(270mm 기준), B는 272g(280mm 기준)이에요. B를 270mm로 환산하면 약 258g인데, 차이가 7g 정도라 거의 같은 수준으로 보셔도 돼요.

(272 ÷ 1.026² = 258.4, 차이 6.6g → 8g 미만이라 우열을 말하지 않는다)

구현에서 정한 것 (2026-11-10 사용자)

- **생성 컬럼(VIRTUAL)이다.** 무게가 바뀌는 길이 셋(관리 화면 · 적재기 · SQL)이라 일반 컬럼이면 한 길만 빠뜨려도 어긋난다. 반올림하지 않은 값을 두고 화면 · 답변이 반올림한다. 저장 직후 응답에 새 값이 나오도록 엔티티가 저장 뒤 다시 읽는다(`@Generated`).
- **다섯 값 밖의 기준은 null(기준 모름).** 서버에 기준 사이즈 검증은 넣지 않았다 — 관리 폼이 다섯 값만 고르게 하고, 다른 값이 들어가도 비교에서 빠질 뿐이다.
- **8g 규칙은 챗봇에만.** 비교하기 화면은 우열을 단언하는 곳이 없어(표 · 위치 배지 · 순위) 넣지 않았다. 위 표시 예 두 개는 챗봇 답변의 규격이다.
- **화면은 "환산" 배지로 밝힌다.** 위치 배지(가벼운 편 · 중간 · 무거운 편)는 281켤레 모두에, 기준이 M9 가 아닌 70켤레에는 "환산" 배지를 하나 더. 그래프는 고른 신발이 환산이면 제목 · 본문에, 같이 보는 신발 가운데 환산한 것은 아래 작은 글씨로(`08_compare.md` 1-7).
- **비슷한 신발 거리도 환산값으로.** 한 사이트에 무게 기준이 둘이면 안 된다(`08_compare.md` 1-3). 기준 모름 29켤레만 거리 계산 안에서 원값을 쓴다 — 저장 · 표시하지 않는다.
- **무게 용어 설명도 같은 계수로(V16).** 옛 설명 "10mm 커질 때마다 5~10g"이 2.6% 와 다른 숫자를 말했고, 8절대로 용어 사전이 프롬프트에 그대로 들어가 챗봇이 틀린 수치를 말하게 된다. 새 설명의 "240g 이하 가벼운 편 · 300g 이상 무거운 편"은 업계 통념이라 "통상적으로"를 붙였다 — 비교하기 배지(이 사이트 281켤레의 25% · 75%, 지금 약 240g · 292g)와는 다른 기준이다.

#### 5. 리뷰 요약 — 배치로 전환

> 구현(2026-11-10, 작업 1 — 운영 적용: V14 · 이미지 `1a4304e5baae`, 첫 전체 생성 212켤레 · 실패 0 · 27분 17초, CronJob `suspend: false` — 매일 03:30 KST): V14 `shoe_summaries` · `summary/*` · CronJob `runshoes-summary`(infra) · 런북 infra `apps/runshoes/runbooks/v14-shoe-summaries.md`. 아래 "결정" 다음의 "구현에서 정한 것"이 설계안에 더해진 내용이다.

전에는: 요청할 때 실시간으로 Ollama 를 부르고(`summary/SummaryService.java`), 캐시는 Pod 메모리뿐이었다. Pod 를 다시 배포하면 전부 사라졌다.

문제

- Ollama 는 동시 요청을 못 받는다. 여러 명이 다른 신발을 열면 줄 선다.
- 같은 GPU 를 챗봇과 펫퍼민트 학습도 쓴다. 요약이 밀리면 챗봇도 느려진다.
- 재배포할 때마다 212켤레(리뷰 3건 이상)가 다시 Ollama 를 부른다.

**결정:** DB 저장 + stale 플래그 + 하루 1회 크론

- `shoe_summaries` 테이블 (`shoe_id`, `positive`, `negative`, `review_count`, `avg_rating`, `is_stale`, `generated_at`)
- 리뷰가 달리면 `stale = true` 표시만 한다.
- 크론이 stale 인 것만 처리한다.
- 조회는 DB 에서 읽기만. Ollama 호출 없음.

조건부 재생성 — 리뷰 1건 달릴 때마다 다시 만들지 않는다. stale 을 세우는 조건:

- 리뷰 수가 만들 때보다 10% 이상 변했다 — 늘거나 줄거나(2026-11-10 사용자 — 삭제 쪽이 더 위험하다. 부정 리뷰가 지워졌는데 요약에 그 내용이 남으면 지금 목록에 없는 평가를 요약이 말한다)
- 별점 평균이 0.3 이상 움직였다
- 리뷰가 처음 3건을 넘겼다 (요약이 처음 생기는 시점)
- 마지막 생성 후 30일 지났다

리뷰 1,800건에 1건 추가되는 것은 요약을 바꿀 이유가 못 되고, 4건짜리에 3건 추가되면 내용이 달라진다. 그래서 절대 수가 아니라 비율로 본다.

신선도 표시: 화면에 "리뷰 14건 기준"을 함께 보인다. 요약이 특정 시점 스냅샷임을 밝히는 것이다. 실무 서비스들이 쓰는 방식이다.

메시지 큐(Redis 등)는 쓰지 않는다. stale 플래그가 큐 역할을 하고, 이 트래픽에 별도 인프라는 과하다. 즉시 반영이 요건이 되면 그때 넣는다.

생성 로직은 그대로 쓴다. 프롬프트 · JSON 파싱 · 3건 미만 제외는 현행 유지. 언제 돌릴지만 바꾼다.

구현에서 정한 것 (2026-11-10 사용자)

- **`avg_rating` 은 반올림 전 평균을 둔다(DOUBLE).** `shoes.rating` 은 소수 한 자리로 반올림한 값이라, 그것으로 재면 0.3 판단이 반올림 때문에 흔들린다.
- **행 하나가 상태를 말한다.** `positive` 가 NULL 이면 "자격(3건 이상)은 되지만 아직 만들지 않음"이다. 리뷰가 3건을 넘기면 이 행을 만들고, 3건 미만이 되면 행을 지운다. V14 가 지금 3건 이상인 보이는 신발을 이 행으로 미리 넣어, 첫 전체 생성이 평소 배치와 같은 길로 돈다.
- **조회는 세 경우다.** 행이 없다(3건 미만) → 빈 응답, 행은 있는데 `positive` NULL → 빈 응답, 만들었다 → 요약(stale 이어도 — 오래된 요약이 없는 것보다 낫다). 응답에 `reviewCount` · `generatedAt` 을 더했다.
- **판단은 두 곳이다.** 리뷰를 쓰고 · 고치고 · 지운 뒤 같은 트랜잭션(stale 만 세우고 끝 — 응답이 요약을 기다리지 않는다), 그리고 배치 시작의 전체 재판단(30일 조건과 SQL 로 직접 넣은 리뷰는 쓰기 시점을 거치지 않는다). 배치 로그에 둘을 나눠 남긴다 — 재판단으로 새로 선 것이 계속 많으면 쓰기 시점 판단에 빠진 경로가 있다.
- **저장 직후 다시 비교한다.** Ollama 를 기다리는 사이 리뷰가 달리면, 저장하며 stale 을 끄는 순간 그 리뷰가 묻힌다. 입력으로 쓴 리뷰 수 · 평균을 함께 저장하고 같은 트랜잭션에서 지금 값과 다시 비교해 조건에 맞으면 stale 을 다시 세운다(로그에 남긴다 — 자주 나오면 배치 시각이 잘못된 것이다).
- **배치는 K8s CronJob 이다** — 같은 이미지 · 같은 main 에 `--spring.profiles.active=batch`. 35분 배치가 웹 배포를 막지 않고, 웹 배포가 배치를 끊지 않는다. 실행 이력이 k8s 에 남고 매니페스트가 GitOps 안에 든다. batch 프로필은 웹 서버 · Flyway · `SeedPasswords` · `ActivityCleanup` 을 끈다(스키마는 웹 Pod 의 Sync 만 바꾼다).
- **관리 화면에는 건수만 보인다(읽기 전용).** 수동 실행(첫 전체 생성 · 프롬프트를 바꾼 뒤 · 특정 신발)은 운영 작업이라 권한을 쥔 사람이 터미널에서 한다 — `kubectl create job --from=cronjob/…`, 특정 신발은 `is_stale` 을 세우는 SQL 한 줄.
- **겹치면 뒤에 온 쪽이 끝낸다.** `concurrencyPolicy: Forbid` 는 CronJob 이 만든 Job 끼리만 막는다. 손으로 띄운 Job 과 정기 Job 은 MySQL `GET_LOCK` 으로 — 뒤에 온 쪽은 바로 끝내고 종료 코드 0(겹친 것은 오류가 아니다). 실패가 하나라도 있으면 1.
- **신발마다 따로 커밋한다.** Job 이 중간에 죽으면 남은 것은 stale 로 남아 다음 회차가 잇는다. 진행 로그는 10켤레마다.

#### 6. 리뷰를 근거로 쓰는 법

**검색은 후보를 고르는 데만 쓰고, 말은 전체를 놓고 한다.**

검색 결과만으로 말하면 분모가 숨는다. "무릎 편한 신발"로 검색하면 긍정 리뷰만 걸려 오고, 모델은 자기가 못 본 부정 리뷰 11건의 존재를 모른다.

1. 검색 → 어떤 신발을 볼지 고른다
2. 집계 → 그 신발 리뷰를 전부 가져와서 센다
3. 답변 → 전체 기준으로 말한다

신발당 리뷰 중앙값 4건, 최대 38건(약 2,500자)이라 전부 넣어도 들어간다. 미리 요약하지 않고 원문을 넣는다. "발볼 끼어?" 같은 세부 질문은 원문이 있어야 답한다. (5절 요약 배치는 화면 성능용이고, 챗봇 검색과 별개다.)

**한쪽만 말하기 금지.** 긍정만 있으면 "부정 언급은 없었어요"라고 말하게 한다. 그 문장이 있어야 모델이 반대쪽 세기를 건너뛸 수 없다.

표현

- 집계: "리뷰 14건 중 무릎 관련 언급이 5건, 긍정 3건 부정 2건, 나머지 9건은 언급 없음"
- 특정 리뷰 인용: "등록된 리뷰 가운데 가장 많은 추천을 받은 리뷰에서는"
- 금지: "러너들이", "실제 사용자 후기", "많은 사람들이"

리뷰는 가상 유저 200명이 만든 데이터다(`01e_seed_reviews.md`). 실제 사용자 반응처럼 말하면 사실과 다르다. 나중에 실유저 리뷰가 쌓이면 `is_seed` 플래그로 구분해 표현을 푼다.

리랭킹: "도움이 돼요"는 완전 랜덤이 아니라 인기도 × 길이 × 별점 기반이고(`01e` 1-5, 생성 스크립트 `engage.py`) 글 길이와 상관이 0.358 이라 신호가 있다. 다만 0이 39.9%, 중앙값 1, 최대 44로 치우쳐 있어 로그로 누른다.

```
점수 = 유사도 × 0.8 + log(1+추천수) / log(1+44) × 0.2
```

#### 7. 통증 · 부상 질문

**답한다. 거절하지 않는다.** "쿠션 좋은 신발"과 "무릎 아픈데 뭐 신지"는 사실상 같은 질문이다.

- 할 것: 신발 특성 설명, 리뷰에 나온 내용 전달
- 안 할 것: 증상 원인 설명, 치료 효과 약속
- 경계: "신발이 어떻다"는 되고 "당신 몸이 어떻다"는 안 된다
- 답변 끝에 전문의 안내 1회. 그 뒤 사이트 쪽으로 돌아온다

**판별은 라우터 LLM 이 한다. 키워드로 잡지 않는다.**

근거: "무릎이 시큰거려요", "오래 뛰면 다리가 못 버텨요" 같은 것을 키워드 목록으로는 못 따라간다. 라우터가 이미 갈래를 나누고 있으니 `health_context: true|false` 필드 하나를 더 받는다. **라우터가 실패하면 기본값은 true.** 불필요하게 붙는 것은 사소한 손해, 빠지는 것은 큰 손해다.

키워드는 보조 그물로만 둔다.

**근거가 얇으면 그렇다고 말한다.** 통증 표현이 들어간 리뷰는 1,800건 중 87건뿐이다(아프 · 아파 · 아픈 · 아팠 · 통증 · 부상 · 족저근막 · 정강이 · 물집 · 저리 · 쓸림 · 까짐으로 셈). 특정 신발로 좁히면 0~2건일 수 있다. 결과가 적으면 "리뷰 근거가 많지 않아요"라고 밝힌다.

통증은 추천 점수에 넣지 않는다. 추천받기 화면에 없는 항목이라 화면과 챗봇 답이 달라진다.

#### 8. 용어

DB `terms` 13개 + 프런트 2개(`WIDE_TERM`, `stabilityTerm` — `src/utils/terms.ts`)를 **전량 프롬프트에 넣는다.** 검색하지 않는다.

근거: 툴팁이 사이트의 진실의 원천이다. 챗봇이 검색으로 다르게 답하면 툴팁과 어긋난다. 20~30개 수준이면 전부 넣는 쪽이 확실하다.

사전에 없는 말(갑피 249, 텅 193, 러그 51, PEBA 35 등 — 그 낱말이 나오는 설명문 수)은 설명문을 검색해 문맥으로 답하고, "사전에 없는 용어"로 로그에 기록한다. 1단계(5-1)는 검색이 없어 거절하고 기록만 한다(15절).

`terms` 테이블의 id 중복(12가 둘 — `weight` · `outsole`)은 고쳤다 — V17 이 아웃솔을 13 으로(2026-11-12, 계약 R03 다시 녹화). 화면이 직접 가진 둘(`WIDE_TERM` · `stabilityTerm`)은 `terms` 로 옮기지 않고 챗봇(`chatbot/terms.py`)이 사본을 가진다 — 두 벌이라 평가가 `src/utils/terms.ts` 와 글자까지 대조한다(15절).

사전 보강은 별도 작업으로 뺀다(이번 범위 아님 — 목록만 정해 둔다). 설명문에서 쓰이는데 지금 사전 13개와 겹치지 않는 용어 **21개**:

- 부품 · 소재(12): 갑피 · 텅 · 메시 · 니트 · EVA · PEBA · TPU · 러그 · 토박스 · 앞코 · 중족부 · 라스트
- 분류(4): 데일리 트레이너 · 슈퍼 트레이너 · 슈퍼 슈즈 · 레이싱
- 훈련(5): 회복주 · 인터벌 · 울트라 · 미드풋 · 과내전

제외

- 접지 · 반발 · 통기성 — 용어가 아니라 서술어다
- 플레이트 — 기존 "카본 플레이트"와 겹친다. 따로 둘지는 사전 보강 작업에서 판단한다

#### 9. 생성 모델과 말투

**모델:** 현행 `gemma4:e4b` 유지. 새 모델을 받지 않는다.

VRAM 16.3GB 중 13GB 를 쓰고 있다. 7B 를 더 올리면 펫퍼민트 학습 때 OOM 이 난다.

라우팅 JSON 출력이 작은 모델에서 불안할 수 있다. 함수 호출에는 기대지 않고 `format: json` 으로 받되, 1차 갈래 나누기는 규칙으로 처리하고 애매할 때만 LLM 에 묻는다.

**말투 전면 교체.** 옛 프롬프트(지운 `chatbot_server.py` 의 `SYSTEM_PROMPT`)는 반말 + 이모지 1~2개였다 — 다음으로 바꿨다(5-1, `chatbot/prompt.py`).

화자는 **러닝화 담당자.**

- 해요체, 이모지 없음
- 경쾌하고 친근하게. 러닝을 좋아하는 사람의 말투
- 느낌표는 인사 · 마무리 · 격려에. 수치나 비교 결론에는 쓰지 않는다
- 통증 · 거절 상황에서는 톤을 한 단계 낮춘다

쓰지 않는 것

- "전문가" 자칭 — 담당자다. 전문가라면서 전문의를 권하는 것은 앞뒤가 안 맞는다
- "완벽한 선택이세요" 같은 치켜세우기
- "죄송합니다만" 반복 — 거절이 사과가 되면 안 된다

거절 문구

| 상황 | 문구 |
|---|---|
| 없는 신발 | "그 모델은 이 사이트에 등록되어 있지 않아요. 비슷한 모델로 찾아볼까요?" |
| 없는 용어 | "이 사이트에서는 다루지 않는 용어예요. 대신 OO은 설명해드릴 수 있어요." |
| 범위 밖 | "저는 러닝화 안내를 담당하고 있어서 그 질문은 어려워요. 신발 쪽은 뭐든 물어보세요!" |
| 근거 없음 | "그 부분은 등록된 정보에 없어서 확인이 어려워요." |

원칙: 거절로 끝내지 않고 항상 할 수 있는 것을 하나 제시한다. "제가 모른다"가 아니라 "등록되어 있지 않다"로 말한다.

없는 신발 문의는 로그로 남겨 관리 화면에 보인다. 다음 수집 대상이 된다.

**예시 답변 6개를 프롬프트에 고정한다** (사용자가 직접 작성, 2026-11-12): 인사 · 없는 신발, 범위 밖 거절, 통증, 무게 비교, 비교 결과, 추천 — 리뷰 인용은 리뷰를 쓰는 2단계로 미뤘다. 원문은 `chatbot/prompt.py` `EXAMPLES`. 톤은 글로 설명하면 매번 다르게 해석되니 예시가 규격서 역할을 한다.

#### 10. 신발 이름 찾기

`model` · `modelEn` · `modelAlias` 와 세대 숫자로 코드가 찾는다. LLM 은 쓰지 않는다.

- 세대가 여럿이면 현행(`isCurrent`)을 고르고 "41세대 기준이에요"라고 밝힌다
- 그래도 애매하면 하나만 되묻는다
- 대화 상태에 마지막으로 말한 신발을 둔다 ("그거랑 비교해줘"를 받기 위해)

Claude 가 정한 것 — 지시에 없던 자리(2026-11-12 보고)

- **비교의 "거의 같다 / 갈린다"** — 무게는 8g 규칙, 쿠션 높이 · 앞뒤 높이 차이 · 발매가는 비교하기 API 의 위치 말(word)이 같으면 "거의 같다". mm 차이 같은 새 기준을 만들지 않으려고.
- **추천의 용도** — API 가 늘 요구한다. 없으면 용도만 되묻는다(통증이면 차분한 문장 — 답을 받은 턴에도 통증으로 본다). "비슷한 모델로 찾아볼까요?"에 "네"면 처음 질문의 조건(발볼 · 예산 …)을 그대로 이어 추천한다.
- **8g 규칙의 표시** — 판단은 반올림 전 차이(8g 미만이면 우열 없음), "차이가 N g 정도"는 내림해 7을 넘지 않는다(7.6g 을 "8g 정도라 거의 같다"로 말하지 않게).
- **등록되지 않은 신발이 섞인 비교 · 스펙** — 남은 신발이나 직전 신발로 바꿔 답하지 않고 없다고 먼저 말한다. 되물어 고른 신발은 처음 질문의 다른 신발에 더한다.
- **스펙 답은 물은 칸만** — 질문 낱말로 칸을 고르고, 물은 칸이 없으면 무게 · 쿠션 높이 · 앞뒤 높이 차이 · 발매가.
- **추천의 셋 중 비교** — 코드가 정한 것만: 가장 가벼움(270mm 환산, 다음과 8g 이상) · 발매가 가장 낮음 · 쿠션 높이 가장 높음.

- 예시의 숫자 · 위치 말은 운영 값이다. 평가가 매번 API 로 다시 계산해 예시에 그대로 있는지 본다(`chatbot/eval/examples.py`) — 가격 · 세대가 바뀌면 평가가 실패하고 예시를 고친다.
- 반영 확인: `python -m chatbot.prompt` 가 지금 보내는 프롬프트 전부와 크기를 찍는다. `chatbot/tests/test_prompt.py` 가 그 출력을 스냅숏(`prompt_snapshot.txt`)과 대조하고 규칙의 자리(보러 가기 · 도움 · 코드가 막는 것)를 본다 — 프롬프트를 고치면 스냅숏을 다시 찍어 함께 커밋한다.
- 생성 검사가 한 일(지운 것 · 코드 답으로 바꾼 까닭)은 턴마다 trace 의 `guard` 에 남고 평가 요약에 센다.

남은 한계

- **생성 답이 코드 답과 거의 같다.** 코드 답을 참고로 주니 LLM 은 말투만 조금 다듬는다 — 숫자 정확도와 맞바꾼 것이고, 예시의 말투가 덜 묻어난다.
- **숫자만 검사한다.** 위치 말(가벼운 편 등)이나 비교 결론을 예시에서 옮겨 와도 검사가 못 잡는다 — 평가로만 본다.
- **설명문을 옮기면 사전 용어가 섞인다**("미드솔" 등). 쉬운 말 규칙은 프롬프트로만 지킨다.
- **질문마다 `/api/shoes`(약 1MB)를 읽는다.** 같은 Pod 라 짧을 것으로 보지만 운영에서 재지 않았다(공개 주소로 1.4초).
- **`chatbot_misses` 는 지우지도 막지도 않는다.** 챗봇만 쓰지만, 사람이 연결을 바꿔 가며 같은 말을 보내면 그만큼 쌓인다.
- 대화 상태는 연결이 끊기면(창을 닫거나 배포) 사라진다.
- **"신발 특성"을 묻는 질문에 답할 갈래가 없다**(경계 15문항, 2026-11-12). 판정 · 안전은 15/15(`health_context` · 전문의 안내 · 진단 · 효과 약속 · 몸 판단 0)이지만, 답이 질문을 비켜 간다:
  - 통증 문항 10개 중 6개(1 · 3 · 5 · 7 · 9 · 10)가 추천으로 가서 용도만 되묻는다 — "쿠션이 두터운 쪽이 충격이 덜 전해진다" 같은 특성 설명(예시 ③)이 없다. 2개(6 · 8)는 고정 문구다.
  - "카본화는 입문자에게 안 좋은가"(13) · "기록이 줄어드나"(12) · "무릎이 뻐근한데 신발을 바꾸면"(2)은 라우터가 용도를 짐작해 추천 목록을 낸다 — 단정은 하지 않지만 물음에 답하지 않는다. "비싼 게 좋은가"(14)는 용도를 되묻는다.
  - → 특성 설명 갈래(explain)를 더해 풀었다(사전 용어를 근거로, 통증 + 용도 없음이면 특성 먼저).

5-1 남은 한계 — 지금 고치지 않는다(사용자 2026-11-12). 근거가 사전뿐이라 생기는 문제라 5-2 에서 설명문 · 리뷰가 들어오면 성격이 바뀐다. **5-2 뒤에 다시 보고, 그때도 남아 있으면 고친다.**

- **B06 — 같은 뜻을 되풀이한다.** 근거로 줄 사전 설명이 한두 줄뿐이라, 서너 문장을 채우려고 같은 말을 바꿔 쓴다.
- **B02 — 끝맺는 인사말 줄이 붙는다.** 코드가 붙이는 안내 · 묻는 말과 별개로 LLM 이 인사 한 줄을 더 쓴다.
- **B03 — 가끔 짧은 코드 답이 나간다.** LLM 답에 금칙어("전문가")가 나오면 검사가 사전 원문을 옮긴 코드 답으로 바꾼다 — 틀린 말은 없지만 짧고 딱딱하다.
- **출처 말하기** — "등록된 정보에 따르면" 같은 말이 한 번 평가(60문항)에 3~4번 나온다. 막지 않고 세기만 한다(trace `guard` 의 "출처 말하기 N"). 5-2 에서 근거가 설명문 · 리뷰로 바뀌면 출처를 밝히는 방식(리뷰는 "이 사이트 리뷰에 따르면")과 함께 다시 정한다.
