# 09 Spring 전환과 API 계약 시험

RUNSHOES의 화면은 처음에 json-server(JSON 파일 하나를 그대로 API로 내주는 간단한 서버)와 이야기했다. 과제 요건이 React와 json-server였기 때문이다. 지금은 같은 API를 Spring Boot와 MySQL이 내준다. [docs:requirements.md:31] 서버를 바꿔 끼우면서 정답으로 삼은 것은 설계 문서가 아니었다. 원래 돌던 json-server의 응답을 실제로 녹화해 두고, 새 서버가 그 응답을 그대로 재현하게 만들었다. 로그인, 권한, 신발 세대, 출처 같은 새 기능은 그 위에 응답의 키를 더하는 방식으로만 얹었다. 바꿀 때마다 녹화본과 견주는 이 검사를 계약 시험이라고 부른다. [docs:05_api_contract.md:10]

## 왜 녹화부터 했나

목표는 화면을 고치지 않고 뒤의 서버만 바꾸는 것이었다. [docs:05_api_contract.md:144] 그러려면 화면이 서버에게서 무엇을 기대하는지 정확히 알아야 한다. 처음에는 코드를 읽고 쓴 이전 계획서가 있었는데, 실제로 응답을 녹화해 보니 계획서와 다른 곳이 넷 나왔다. 계획서는 API 응답을 브라우저가 저장하지 못하게(`no-store`) 한다고 적었지만 실제 응답은 저장하되 매번 확인하라(`no-cache`)였다. 서버 코드에는 `no-store` 가 적혀 있었는데 json-server의 기본 설정이 그것을 덮어쓰고 있었다. 삭제 응답은 지운 문서가 아니라 빈 객체 `{}` 였고, 브라우저가 먼저 보내는 확인 요청(OPTIONS)의 답은 200이 아니라 204였고, 모르는 조건은 무시되는 것이 아니라 "있는 칸이면 거르기"였다. 새 서버는 계획서가 아니라 녹화를 따랐다. [docs:05_api_contract.md:144] [docs:05_api_contract.md:152]

원래 json-server 앱의 녹화는 50건, 리뷰 요약 쪽 9건이다(2026-10-18 녹화). 이 녹화는 지금도 이력으로 남아 있다. [docs:05_api_contract.md:128]

## 계약 시험은 어떻게 도나

시나리오 파일에는 보낼 요청과 기대하는 상태 코드, 다음 단계로 넘길 값(방금 만든 신발의 번호 같은 것)이 차례로 적혀 있다. 녹화 도구가 그것을 차례로 보내 요청, 상태, 머리글, 본문을 파일로 남기고, 비교 도구가 두 녹화를 견주어 통과와 실패를 센다. 실패가 하나라도 있으면 실패로 끝난다. [docs:05_api_contract.md:119-123] 시험은 매번 새로 띄운 임시 데이터베이스에서 돌아, 개발용 데이터베이스를 건드리지 않는다. [docs:05_api_contract.md:136] 녹화에는 비밀번호와 로그인 토큰을 남기지 않고 가린다. [docs:05_api_contract.md:139]

견줄 때는 무엇을 같다고 볼지가 중요하다. 시각은 표기가 달라도 같은 순간이면 같다고 보고, 숫자는 아주 작은 오차를 무시하고, 객체 안 키의 순서는 보지 않는다. 하지만 배열은 순서까지 본다. 정렬했을 때 값이 같은 항목이 번호 순으로 놓이는 것까지 화면이 기대는 계약이기 때문이다. 수정 시각처럼 매번 달라지는 값은 형식만 본다. [docs:05_api_contract.md:138]

## 이상해 보이는 것도 계약이다

녹화에는 처음 보면 이상한 동작이 여럿 있었다. 삭제하면 빈 객체 `{}` 를 돌려주고, 확인 요청에는 204로 답하고, 값이 같으면 번호 순으로 줄 선다. 이것들은 화면이 기대고 있는 동작이라 그대로 두었다. [docs:05_api_contract.md:145] 그래서 응답 머리글도 Spring이 기본으로 주는 교차 출처 허용 기능을 쓰지 않고 필터 하나가 직접 만든다. 기본 기능이 내는 모양이 json-server와 다르기 때문이다. [docs:05_api_contract.md:60] 목록을 거르고 정렬하는 일도 SQL이 아니라 서버 메모리에서 한다. json-server는 값을 자바스크립트 문자열로 견주어서 평점 조건 `rating=4` 는 맞고 `4.0` 은 맞지 않는데, 이런 동작을 SQL로 흉내 내는 것보다 그대로 재현하는 쪽이 정확하다. [docs:05_api_contract.md:55] [docs:05_api_contract.md:61]

다만 녹화에 없고 화면도 쓰지 않는 json-server 동작까지 따르지는 않았다. 그런 것은 안전한 쪽으로 바꿨다. [docs:05_api_contract.md:105] [docs:05_api_contract.md:145]

| 경우 | json-server | RUNSHOES |
|---|---|---|
| 모르는 칸이 온 요청 | 그대로 저장하고 돌려준다 | 버린다 [docs:05_api_contract.md:109] |
| 칸의 값 종류가 다름 | 그대로 저장한다 | 거절한다(400) [docs:05_api_contract.md:110] |
| 없는 신발에 단 리뷰 | 받는다 | 거절한다(400) [docs:05_api_contract.md:111] |
| 리뷰 작성 시각 | 보낸 값을 쓴다 | 언제나 서버 시각 [docs:05_api_contract.md:113] |
| 신발 삭제 | 신발과 리뷰를 지운다 | 숨긴다. 영구 삭제는 관리 API로 따로 [docs:05_api_contract.md:114] |

평점, 찜 수, 작성자, 작성 시각처럼 서버가 정해야 하는 값도 요청 본문을 믿지 않는다. 본문에서 받으면 누구나 바꿀 수 있기 때문이고, 관리자가 보내도 버린다. [docs:05_api_contract.md:148]

## 바꿔 끼운 날

로컬에서 만든 서버 프로그램과 이미지로 시나리오를 돌려 통과 47, 실패 0을 확인했다(2026-10-21). [docs:05_api_contract.md:153] 운영에서는 데이터베이스를 먼저 띄우고, 새 앱 이미지와 배포 설정 변경은 한 번에 내보냈다. 새 이미지가 데이터베이스 설정 없이 뜨는 틈을 만들지 않으려는 것이다. 바꾸는 동안 공개 용어 API를 1초마다 불러 90회 동안 실패가 0이었고, 옛 Pod와 새 Pod가 겹친 2초 동안은 json-server와 Spring이 번갈아 답했다(2026-10-21). [docs:06_deployment.md:166] 전환 직후 운영에서 읽기 전용 시나리오를 돌려 통과 23, 실패 0이었다(2026-10-21). [docs:05_api_contract.md:153] 옛 서버로 돌아가는 길은 새 데이터베이스 구조를 적용한 뒤 데이터와 맞지 않게 되어 같은 날 닫았다. [docs:06_deployment.md:166]

## 그 뒤로 얹은 것

신발 응답에 새 칸이 필요할 때는 옛 키의 순서와 값을 그대로 두고 끝에 더한다. [docs:05_api_contract.md:87] 화면, 데이터 적재기, 계약 시험이 모두 옛 키에 기대고 있어서, 키 하나를 바꾸거나 빼면 셋이 함께 깨진다. 그래서 와이드 모델을 국내와 해외로 나눌 때도 기존의 "와이드 있음" 칸은 두고 범위 칸을 따로 더했다. [docs:05_api_contract.md:146] 옛 녹화와 견줄 때 비교 도구는 "응답에 정해 둔 키가 더해졌을 뿐인지"만 본다. [docs:05_api_contract.md:137] 서버 쪽에서 막으면 옛 계약이 깨지는 검사는 관리 화면의 입력 폼이 맡기도 한다. [docs:05_api_contract.md:101]

로그인을 더할 때는 새 녹화를 굳히기 전에 옛 기준선(98건)과 먼저 견주어 95건이 통과하는 것을 보고, 기존 계약을 바꾸지 않았음을 확인한 뒤에 새 시나리오 17건을 기대 상태와 본문을 읽어 가며 더했다(2026-10-21). [docs:05_api_contract.md:154] 계약을 일부러 바꾼 경우는 실패로 남기고 까닭을 적는다. 로그인을 더한 뒤의 기준선에는 그런 실패가 12건 있고(2026-11-10 로컬), 체험 관리자 계정이 번호 하나를 가져가 새 가입 계정의 번호가 밀린 것, 신발 삭제가 숨김이 되어 새 신발 번호가 하나 밀린 것, 지운 리뷰 번호를 다시 쓰지 않게 바뀐 것, 용어 설명을 고친 것이 그 까닭이다. [docs:05_api_contract.md:6] [docs:05_api_contract.md:156] 지운 번호를 다시 쓰지 않게 된 것은, 서버가 가장 큰 번호에 하나를 더해 매기던 방식이 배포 중 두 Pod에서 같은 번호를 내어 충돌했기 때문이다. 데이터베이스가 번호를 매기게 바꾸며 이 계약 변경을 받아들였다(→ 「배포」). [docs:05_api_contract.md:155]

계약 시험은 버그도 찾았다. 탈퇴한 뒤 남아 있던 로그인 토큰(15분짜리)으로 자기 리뷰를 고치고 지우는 것이 통과했는데, 어디서나 거절하도록 고치고 그 장면을 녹화해 기준선에 더했다. [docs:05_api_contract.md:160] 새 기능의 시나리오를 모은 기준선은 지금 통과 201, 실패 0이다(2026-11-15 로컬). [docs:05_api_contract.md:6]

## 무엇이 어려웠나

무엇을 정답으로 삼을지가 첫 갈림길이었다. 코드를 읽고 쓴 계획서가 이미 있었고, 그것을 따라 만들어도 그럴듯해 보였다. 하지만 녹화해 보니 계획서가 틀린 곳이 넷이었고, 그 넷은 모두 화면이 실제로 받던 응답이었다. 그래서 문서나 계획서가 아니라 실제 응답을 정답으로 삼았다. [docs:05_api_contract.md:144] [docs:05_api_contract.md:152]

기준선을 다시 녹화할지도 갈림길이었다. 응답이 바뀔 때마다 새로 녹화하면 시험은 늘 깨끗하게 통과한다. 하지만 그러면 무엇이 언제 바뀌었는지의 흔적이 사라진다. 그래서 옛 기준선은 그대로 두고, 더해도 되는 키 목록과 "일부러 바꾼 차이" 목록을 함께 둔다. 이 셋이 곧 계약의 변경 이력이 된다. [docs:05_api_contract.md:147]

## 용어 풀이

- json-server: JSON 파일 하나를 읽고 쓰는 API로 바로 내주는 간단한 서버. 과제 요건이었다
- API 계약: 이 요청을 보내면 이 모양의 응답이 온다는, 화면과 서버 사이의 약속
- 기준선: 정답으로 삼아 남겨 둔 녹화. 새 서버의 응답을 이것과 견준다
- 계약 시험: 시나리오를 보내 새 응답을 녹화하고 기준선과 견주어 달라진 곳을 찾는 시험
