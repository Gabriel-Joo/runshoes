# 10 배포

코드를 저장소의 main 가지에 올리면(push) 운영까지 사람이 손대지 않는다. Jenkins가 이미지(프로그램과 실행 환경을 통째로 묶은 꾸러미)를 만들어 Harbor(이미지 보관소)에 올리고, 인프라 저장소에 적힌 이미지 태그 한 줄을 바꿔 커밋한다. ArgoCD는 그 커밋을 읽어 클러스터를 맞춘다. Jenkins와 ArgoCD는 서로를 부르지 않고 Git만 본다. [docs:06_deployment.md:10] push에서 새 Pod(함께 뜨고 함께 내려가는 프로그램 묶음)가 뜨기까지 약 5분 걸린다(2026-11-09 측정). [docs:06_deployment.md:31] 데이터베이스 구조를 바꾸는 배포만은 예외로, 사람이 자동 반영을 끄고 순서대로 연다. [docs:06_deployment.md:10]

## 흐름

GitHub는 push를 받으면 웹훅(일이 생기면 상대에게 바로 알려 주는 호출)으로 Jenkins를 부른다. 웹훅을 놓쳐도 Jenkins가 15분마다, ArgoCD가 3분마다 저장소를 살피는 폴링이 안전망으로 잡는다. [docs:06_deployment.md:155] Jenkins는 이미지 두 개를 만든다. 화면과 Spring 서버가 든 이미지와 챗봇 이미지다. 두 이미지는 같은 태그를 달고, 그 태그는 커밋 해시의 앞 12자리다. `latest` 같은 이름은 쓰지 않아서, 태그만 보면 어느 커밋이 돌고 있는지 안다. [docs:06_deployment.md:55]

이미지가 Harbor에 올라가도 그것만으로는 배포되지 않는다. ArgoCD는 이미지 보관소를 보지 않고, Git에 새 태그가 적혀야 움직인다. 태그 커밋 한 줄이 Harbor와 ArgoCD를 잇는 유일한 다리다. [docs:06_deployment.md:153] Jenkins가 클러스터에 새 이미지를 직접 밀어 넣지 않는 것은, 그러려면 Jenkins가 클러스터 권한을 쥐어야 하고 무엇이 배포됐는지 알려면 클러스터에 직접 물어야 하기 때문이다. 이렇게 두면 배포된 것의 답이 늘 Git에 있고, 되돌리기는 커밋 하나를 되돌리는 일이 된다. [docs:06_deployment.md:152] 앱 저장소와 인프라 저장소를 나눈 것도 같은 맥락이다. 같은 설정이 두 곳에 있으면 어느 쪽이 진짜인지 다투게 되고, 인프라 저장소 하나를 보면 클러스터 전체가 보인다. [docs:06_deployment.md:154]

## Jenkins가 하는 일

Jenkins 작업은 세 단계다. 커밋 해시로 태그를 정하고, 두 이미지를 만들어 올리고, 인프라 저장소의 태그를 고쳐 커밋한다. [docs:06_deployment.md:61] 태그 두 줄은 한 번에 바꾸고, 바뀐 줄이 정확히 두 줄인지 센다. 한쪽 이미지만 바뀌는 배포를 막으려는 것이다. [docs:06_deployment.md:65] 인프라 저장소는 Jenkins의 저장소 받기 기능이 아니라 셸 명령으로 받는다. 그 기능으로 받으면 Jenkins가 인프라 저장소까지 살피게 되어, 태그를 push할 때마다 빌드가 다시 불리는 고리가 생긴다. [docs:06_deployment.md:66] 다른 프로젝트의 Jenkins도 같은 인프라 저장소에 push하므로, push가 실패하면 최신 상태 위에서 세 번까지 다시 한다. [docs:06_deployment.md:67] 자격 증명은 셸 환경변수로만 다루고 로그에 찍히지 않게 한다. [docs:06_deployment.md:68]

이미지 안의 Java 실행 환경은 필요한 모듈만 골라 줄였다. 그대로 쓰면 421MB인 이미지가 252MB가 된다(2026-11-02 기준). 대신 필요한 모듈이 빠지면 실행 중에야 오류로 드러나므로, 의존성을 더하면 계약 시험을 다시 돈다(→ 「Spring 전환과 API 계약 시험」). [docs:06_deployment.md:56] 이미지를 만드는 컨테이너는 특권 권한 없이, 꼭 필요한 보안 제한 두 가지만 풀고 돈다. [docs:06_deployment.md:57]

## 클러스터에서

앱은 Pod 두 개로 돌고, 둘은 서로 다른 노드(클러스터를 이루는 가상 머신)에 놓인다. 노드 하나가 죽어도 다른 Pod가 받고, 정비로 노드를 비울 때도 최소 하나는 남긴다. [docs:06_deployment.md:85] 새 이미지로 바꿀 때는 옛 Pod 하나를 먼저 내리고 그 자리에 새 Pod를 띄운다. 앱이 놓일 노드가 둘뿐이라 세 번째 Pod를 띄울 자리가 없어서다. 그동안은 남은 Pod 하나가 요청을 받는다. 새 Pod는 데이터베이스까지 닿아야 준비됐다고 알린다. [docs:06_deployment.md:88]

비밀값(로그인 서명 키, 데이터베이스 비밀번호 등)은 사람이 클러스터에 넣는다. 비밀값이 없으면 새 Pod는 멈추고 옛 Pod가 계속 돈다. [docs:06_deployment.md:89] 네임스페이스(클러스터 안에서 한 서비스의 자원을 묶는 칸)도 사람이 만든다. ArgoCD가 그것을 소유하면, 앱 설정을 지우거나 정리하는 한 번에 비밀값까지 사라질 수 있다. [docs:06_deployment.md:90]

ArgoCD는 자동으로 반영하되 두 가지를 껐다. 하나는 클러스터를 Git과 다르게 바꾸면 되돌려 놓는 기능이다. 복구하는 중에 사람이 손으로 바꾼 것을 되돌리지 않게 껐다. 다른 하나는 Git에서 지운 자원을 클러스터에서도 지우는 기능이다. 데이터가 든 디스크를 실수로 지우지 않게 껐다. [docs:06_deployment.md:96-97] 자동 반영을 끄고 켜는 스위치는 클러스터에서 사람이 직접 누른다. [docs:06_deployment.md:99]

서버의 상태 점검 창구는 공개 주소에서 떼어, 클러스터 안에서만 닿는 관리용 포트로 옮기고 있다. 그대로 두면 인터넷에 열려 있고, 성능 지표를 내보내는 창구를 더하면 그것까지 열린다. 다만 창구를 먼저 옮기면 Pod가 준비됐는지 묻는 점검이 깨져 배포가 멈추므로, 새 점검 주소를 먼저 더하고, 클러스터의 점검을 그쪽으로 바꾸고, 마지막에 옮기는 세 단계로 나눴다. [docs:06_deployment.md:130] 앞의 두 단계는 끝났고, 마지막 단계는 앱 쪽만 로컬에서 끝났으며 지표를 긁어 가게 하는 표시는 인프라 쪽 일로 남아 있다. [docs:06_deployment.md:134-136]

## 데이터베이스 구조를 바꾸는 배포

서버는 뜰 때 데이터베이스 구조 변경(마이그레이션)을 스스로 적용한다. 그래서 새 마이그레이션이 든 이미지는 반영되는 순간이 곧 운영 데이터베이스가 바뀌는 순간이다. 이때는 사람이 자동 반영을 끄고, 새 태그가 커밋된 뒤 운영 데이터를 백업(덤프)해 다른 곳에 복원해 맞춰 본 다음, 사람이 반영하고, 로그와 행 수를 확인한 뒤 자동 반영을 다시 켠다. [docs:06_deployment.md:103-111] 마이그레이션마다 이 순서를 적은 런북이 인프라 저장소에 있고, 끝에 실행 기록을 남긴다. [docs:06_deployment.md:114]

배포를 되돌릴 때는 인프라 저장소의 태그 커밋을 되돌린다. 하지만 데이터베이스 구조는 돌아오지 않는다. 마이그레이션은 더하기만 하므로 옛 이미지가 새 구조 위에서 뜬다. 데이터가 잘못됐으면 덤프로 복원한다. [docs:06_deployment.md:116]

배포 방식이 코드에 남긴 흔적도 있다. 앱은 원래 가장 큰 번호에 하나를 더해 새 번호를 매겼는데, 배포 중 Pod가 둘인 순간 두 Pod가 같은 번호를 매겨 충돌했다. "Pod는 하나"라는 가정이 롤링 배포(Pod를 하나씩 차례로 바꾸는 배포)에서는 성립하지 않는다. 지금은 데이터베이스가 번호를 매긴다. [docs:06_deployment.md:168]

## 무엇이 어려웠나

문서만 바뀐 커밋을 어떻게 다룰지가 갈림길이었다. 문서는 이미지에 들어가지 않으므로 이미지를 다시 만들어도 내용이 같은 이미지에 새 태그만 붙고, Pod만 한 번 더 바뀐다. 문서만 바꾼 커밋은 122개 가운데 11개였다(2026-11-09 기준). [docs:06_deployment.md:156] [docs:06_deployment.md:170] 빌드를 부르는 조건에서 문서 경로를 빼는 길도 있었다. 하지만 그러면 push했는데 빌드가 아예 없는 경우가 생기고, 그것이 "조용한 고장"인지 아닌지 가를 수 없게 된다. 그래서 push마다 빌드는 늘 돌리고, 빌드 안에서 바뀐 파일이 모두 문서면 이미지와 태그 단계만 건너뛰게 했다. 무엇이 바뀌었는지 모르면 언제나 빌드하는 쪽으로 간다. [docs:06_deployment.md:63] [docs:06_deployment.md:156] 신발 데이터를 모으는 폴더도 이미지에 들어가지 않지만 건너뛸 목록에 넣지 않았다. 건너뛸 목록이 넓을수록, 나중에 이미지에 들어가는 파일을 새로 더했을 때 배포가 조용히 빠질 위험이 커진다. [docs:06_deployment.md:170]

데이터베이스 구조를 바꿀 때만 사람이 반영하는 것도 고른 일이다. 자동 반영은 태그 커밋을 3분 안에 내보내 "덤프를 뜬 뒤 반영"이라는 순서를 깬다. 평소 배포는 자동이 낫고, MySQL의 구조 변경은 중간에 되돌릴 수 있는 묶음 처리가 아니라서 되돌릴 수 없는 그 순간에만 사람이 문을 연다. [docs:06_deployment.md:157]

## 알려진 한계

- MySQL이 죽었을 때 자동으로 넘어가는 장치가 없다. 그러려면 전용 운영 도구가 필요한데 자원이 모자라, 복제본을 두고 사람이 런북대로 승격하는 쪽을 골랐다. [docs:06_deployment.md:176]
- 구조를 바꾸는 배포는 사람이 세 번 손댄다(자동 반영 끄기, 반영, 켜기). 빼먹으면 덤프 전에 배포된다. 평소 배포는 자동이 낫고 되돌릴 수 없는 순간에만 사람이 문을 연다는 선택의 대가다. [docs:06_deployment.md:178]
- 배포를 이전 이미지로 되돌리는 일은 실제로 해 본 적이 없다. 되돌리는 방법은 런북에 실패 대비로 적혀 있을 뿐이고, 되돌린 뒤 다음 배포가 태그를 다시 덮을 때까지 무엇을 고칠지도 정해지지 않았다. [docs:06_deployment.md:179]
- 이 서비스 전체에 걸린 한계와 조건은 → 「알려진 한계」 한 편에 모았다.

## 용어 풀이

- 이미지: 프로그램과 실행 환경을 통째로 묶은 꾸러미. 클러스터는 이것을 받아 Pod로 띄운다
- 태그: 이미지에 붙이는 이름표. 여기서는 커밋 해시 앞 12자리 [docs:06_deployment.md:55]
- Sync(반영): ArgoCD가 Git에 적힌 상태대로 클러스터를 맞추는 일
- 마이그레이션: 데이터베이스 구조를 바꾸는 단계. 서버가 뜰 때 아직 적용하지 않은 것을 적용한다
